# 変異テストの回し直しの範囲と負荷を抑える判断

## Context

走査の上限のテスト整理で、テストを足した後に変異テストを最終のテストの状態で回し直している最中、CPU が 100% に張り付いて利用者の PC の他の作業が止まりかけ、実行を途中で止めた。
"scripts/mutants.sh" はメモリの上限だけをかけ、CPU の優先度は下げておらず、回し直しのたびに全ての変異を回すため一回に 30 分前後かかっていた。
加えて、走査の一覧と走査の上限の整理では、決着の対象の関数の中の見逃しのうち別のトピックの範囲に当たるものを引き継ぎ先を書いて記録だけにしており、[REQ-testing-012](../../ir/testing/methods.md#REQ-testing-012) が認める三つの決着と食い違うとレビューで指摘され、利用者は受け入れたうえで IR の改訂を求めた。
この三点を決める。

## Agreements

- A1 "scripts/mutants.sh" は cargo-mutants のサービスを CPUWeight=idle と Nice=19 で起動し、他の作業が CPU を使うときはそちらを優先させる。
  - why: 変異テストのビルドとテストが CPU を占め、利用者の他の作業が止まりかけた。優先度を下げても変異テストの結果は変わらない。
  - decided_by: 利用者（推奨を採用）
- A2 最後の変異テストの後にテストを足すだけ（消す・書き換えるを含まない）の変更をしたときの回し直しは、前回の最後まで終わった実行で caught にならなかった変異だけを回せばよい。回し方は、前回の実行の出力を残したうえでの cargo-mutants の --iterate か、前回の見逃しとタイムアウトを含む関数に絞った --re とし、結果は前回の実行の記録と合わせて読む。前回の実行が途中で止まったか、メモリ上限で強制終了されたときは、この回し直しの比べる相手にしない。
  - why: テストを足すだけでは、前回 caught だった変異が見逃しに変わることはないため、全ての変異を回し直しても待ち時間と負荷だけが増える。
  - decided_by: 利用者（推奨を採用）
- A3 トピックごとのテスト整理の変異テストで、決着の対象の関数の中の見逃しでも、凍結中の TUI、既存の FLAG、別のトピックの範囲に当たるものは、テストの追加・同等変異の登録・FLAG の記録の代わりに、どの範囲に当たるかと引き継ぎ先（FLAG の ID かトピックの名前）を記録に書いて決着とする。範囲の当て方は利用者が記録を読んで確かめる。
  - why: その整理で書き足すテストでは決着できず、凍結中の TUI に触れるか別のトピックを先取りすることになるため。走査の一覧と走査の上限の整理で利用者がこの扱いを受け入れた。
  - decided_by: 利用者（推奨を採用）
