走査は [2026-10-05-quality-scan.md](./2026-10-05-quality-scan.md)、設定は [2026-10-05-quality-config.md](./2026-10-05-quality-config.md)、merge の書き込みは [2026-10-05-quality-merge.md](./2026-10-05-quality-merge.md)、バックアップは [2026-10-05-quality-backup.md](./2026-10-05-quality-backup.md)、SSH は [2026-10-05-quality-ssh.md](./2026-10-05-quality-ssh.md) に置く。

## Agreements

- A1 diff は、パスの引数が絶対パスか ".." の要素を含むとき、ローカル・SSH・エージェントのどの経路でも、走査や読み込みの前の引数の段階でコマンド全体を止める。文言は今の "absolute subpath not allowed: パス" と "path traversal not allowed: パス" とし、終了コードは 2 とする。root_dir 全体を指す "/" の指定は従来どおり受け付ける（D2）。
  - why: 絶対パスと ".." の引数がローカル・SSH・エージェントで 3 通りの意味になっていた（指摘 routes-11・diff-14）。引数の誤りは他のファイルを処理する前に止めるほうが安全で、merge の今の止め方とも合う。merge・sync 側は [2026-10-05-quality-merge.md の A1](./2026-10-05-quality-merge.md#A1) に置く。
  - decided_by: 利用者（2026-10-05、品質レビューの判断 D2 を推奨どおり採用）
- A2 ファイルの大きさの上限は、diff・status・merge・sync・rollback とバックアップのための読み込みを含むすべての操作とすべての経路で一つ（104,857,600 バイト）とし、中身を読む前にファイルの大きさで判定する。上限は新しい指定を足さずに --force で一律に外し、--force を指定したコマンドではそのコマンドが行うバックアップのための読み込みにも上限を当てない。上限を超えたファイルは、各コマンドの読めなかったファイルの扱いに従う（D3）。
  - why: 上限が経路・一括と個別・エージェント・バックアップで違い、同じファイルが経路によって成功したり失敗したりしていた（指摘 routes-10・diff-2・merge_sync-5・backup_rollback-3）。台帳の推奨は専用の指定（例 --max-file-size）だったが、利用者は台帳の代案を採り、上限を一つにして --force で一律に外すことにした。上限の値は今の実装の定数 MAX_BINARY_FILE_SIZE の値をそのまま使う。rollback の --force も、この判断により、復元の前に行うバックアップのための読み込みの上限を外すと読んだ。--force を持たないコマンド（status）の扱いは [A12](#A12) で決めた。
  - decided_by: 利用者（2026-10-05、品質レビューの判断 D3 を推奨どおり採用。上限を外す指定は台帳の代案の --force を利用者が選んだ）
- A3 status が、サイズが同じ二つのファイルの更新時刻だけで "equal" と判定するのは、両側がともに秒より細かい精度の更新時刻を持ち、両側に共通する最も細かい精度で比べて同じときに限る。片側でも更新時刻が秒の精度しかなく秒が同じときは、"equal" とせず中身を読み比べる（D8）。
  - why: 更新時刻の精度がローカル（秒）・SSH（小数の秒）・SSH の symlink（秒）・エージェント（ナノ秒）で違い、同じ組でも経路によって判定が変わっていた（指摘 routes-9・status_scan-12）。台帳の推奨は秒にそろえることだったが、利用者は各側が出せる最も細かい精度で比べ、秒しかない側で秒が同じなら中身で比べることにした。同じ秒の中で同じ大きさに編集されたファイルを "equal" と誤る余地をなくすためである。両側の精度が違うときに共通する精度で比べることは、この答えの読み方として書いた。
  - decided_by: 利用者（2026-10-05、品質レビューの判断 D8 を推奨どおり採用。比べる精度は利用者が詰めた答え）
- A4 diff は、パスの数と走査方式によらず次の規則で比べる。名前で指定したファイルは中身で比べる。名前で指定したファイルには include と exclude を当てず、ディレクトリの展開とパスを指定しない diff の走査には include と exclude を当てる。子がすべて exclude に当たるディレクトリを左右の両方にあるときに指定した diff は、include の外のディレクトリの [REQ-cli-077](../../ir/cli/directory-paths.md#REQ-cli-077) と同じく差分なし・終了コード 0 とする。symlink はパスを指定しない diff にも [REQ-cli-020](../../ir/cli/symlink-diff.md#REQ-cli-020) と [REQ-cli-021](../../ir/cli/symlink-diff.md#REQ-cli-021) を当て、リンク文字列も参照先の中身も同じ symlink はどの走査方式でも項目に出さない。中身の同じバイナリはどの走査方式でも項目に出さない。件数の上限を超えたときはどの走査方式でも読めた分を残して errors に載せる。通常のディレクトリと通常ファイルの組は EX-cli-061 にならい、種類の差とディレクトリ側の子とファイル側の本文を示す（D11）。
  - why: 同じファイルの判定と出力がパスの数で変わっていた（指摘 diff-8〜11・13・15）。名前で指定したファイルは利用者が比べたいと示したものなので中身で比べ、フィルタも当てない。FLAG-cli-031 を閉じるため、include と子がすべて除外のディレクトリも同じ規則に入れた。FLAG-cli-054 を閉じるため、同じ symlink を項目に出さないことを明記した。FLAG-cli-047 は、パスを指定しない diff にも REQ-cli-020 と REQ-cli-021 が当たると読むことで閉じる。中身の同じバイナリを項目に出さないため、承認済みの [REQ-cli-009](../../ir/cli/binary.md#REQ-cli-009) の「一致を示す」を書き換える。
  - decided_by: 利用者（2026-10-05、品質レビューの判断 D11 を推奨どおり採用。フィルタと同じ symlink の扱いは利用者が詰めた答え）
- A5 status と diff は、比べるべきファイルの中身を読めなかったとき、そのファイルを空とも同じともみなさず、メタデータの判定のまま残さない。そのファイルのパスと理由を JSON では errors に、テキストでは標準エラーに出し、他のファイルの比較を続けて終了コード 2 を返す。diff の --ref の参照先を読めないときは [REQ-cli-063](../../ir/cli/reference.md#REQ-cli-063) どおり "ref" だけを出し、参照先にないときと区別して理由を errors に出す（D19）。
  - why: status は読めないファイルを理由なしに "modified" や "equal" にし、diff は片側を空として全行を差分にし、--ref の読み込みの失敗は参照先にないことになっていた（指摘 status_scan-6・diff-1・diff-5・diff-6・diff-18）。merge は [REQ-merge-017](../../ir/merge/read-failure.md#REQ-merge-017)、diff の symlink の参照先は [REQ-cli-022](../../ir/cli/symlink-diff.md#REQ-cli-022) が既に同じ方針である。status の出し方は [A14](#A14) で決めた。
  - decided_by: 利用者（2026-10-05、品質レビューの判断 D19 を推奨どおり採用）
- A6 status の --checksum は symlink の組をどの経路でもリンク先の文字列で比べ、辿った先の中身を読まない。--checksum のないときの [REQ-cli-028](../../ir/cli/status.md#REQ-cli-028) と同じ規則にする（D20）。
  - why: ハッシュの経路と中身の経路で symlink の判定が違い、どちらになるかがエージェントの有無のような付随的な条件で決まっていた（指摘 status_scan-8）。リンク先の中身の違いを見たいときは diff を使う。
  - decided_by: 利用者（2026-10-05、品質レビューの判断 D20 を推奨どおり採用）
- A7 merge と sync の --dry-run は、failed があれば実行時と同じく終了コード 2 を返す。sync の --dry-run の書き込み先の状態は、書き込む予定のファイルを書き込めたファイルとして TBL-cli-007 で決める（予定と失敗があれば "partial"）（D27）。
  - why: [REQ-cli-004](../../ir/cli/safety.md#REQ-cli-004) は dry-run が書き込まないことだけを求めており、結果の正直さは実行時と同じにする。旧資料のように dry-run を常に 0 にすると、CI で dry-run を前段の検査に使ったときに読めないファイルを見落とす。sync の dry-run は予定があっても "failed" にしていて実行時の "partial" と食い違っていた（指摘 merge_sync-12）。
  - decided_by: 利用者（2026-10-05、品質レビューの判断 D27 を推奨どおり採用）
- A8 テキストとバイナリの判定は、NUL を先頭 8,192 バイトで調べ、UTF-8 としての正しさをファイル全体で調べ、全体が正しい UTF-8 で先頭 8,192 バイトに NUL がないときだけテキストとする。先頭 8,192 バイトの境目で切れた多バイトの文字は不正としない（D28）。
  - why: 8,192 バイトより後ろの不正なバイトが置換文字になり、diff が差分なしと言い、hunk の merge が選ばなかった部分まで書き換えていた（指摘 diff-17・merge_sync-8）。承認済みの [REQ-cli-061](../../ir/cli/binary.md#REQ-cli-061) の判定の文言を書き換える。大きいファイルでは判定のためだけに全体を読むことになる。
  - decided_by: 利用者（2026-10-05、品質レビューの判断 D28 を推奨どおり採用）
- A9 --ref を使い --force のないファイル全体の merge は、ファイルが「ない」ことと読み込みに失敗したことを区別し、三者の存在の組み合わせで判断する。読み込み元にあり書き込み先にも参照先にもない新しいファイルは --force なしで書く。参照先にあり書き込み先にないファイルは書かずに failed に error "destination changed since reference" で出す。読み込みに失敗したときだけ error "three-way comparison incomplete" で failed に出す。ない側は読みに行かない（D29）。
  - why: 左にだけある新しいファイルが --force なしでは書けず、ない側を読みに行ってエージェントを無効にしていた（指摘 merge_sync-4・merge_sync-3）。[REQ-cli-051](../../ir/cli/merge.md#REQ-cli-051) の対象（三つとも読めた通常ファイル）を存在の組み合わせまで広げる。読み込み元と書き込み先にあり参照先にないファイルの扱いは [A13](#A13) で決めた。
  - decided_by: 利用者（2026-10-05、品質レビューの判断 D29 を推奨どおり採用）
- A10 diff は、片側にだけある 0 バイトのファイルを片側だけの項目として出して差分ありとし（終了コード 1）、片側にだけあり比べるファイルのないディレクトリを指定したときは "not found on either side" を出さず、比べるファイル 0 件・差分なし（終了コード 0）とする。展開した子の、ない側を空とみなす警告は走査方式によらず出さない（D30）。
  - why: 0 バイトのファイルの存在の差が見えず、存在するディレクトリを「どちらにもない」と報告し、警告の有無が走査方式で変わっていた（指摘 diff-20）。diff はファイルを比べるのでディレクトリそのものの存在の差は出さず、それを見たいときは status を使う。
  - decided_by: 利用者（2026-10-05、品質レビューの判断 D30 を推奨どおり採用）
- A11 logs --level は、指定した水準とそれより重い水準の記録を出す（--level warn で WARN と ERROR）。error・warn・info・debug・trace の五つの名前以外はエラーにする（D32）。
  - why: 完全一致で絞るため、誤記や水準の想定違いで黙って何も返さなかった（指摘 config_cli-11）。特定の水準だけを見る使い方はできなくなる。名前の大文字と小文字の扱いとエラーの文言は [A16](#A16) で実装者に委ねた。
  - decided_by: 利用者（2026-10-05、品質レビューの判断 D32 を推奨どおり採用）
- A12 status はファイルの中身をメモリに持たず、中身を少しずつ読みながらハッシュを計算して比べる。そのため [A2](#A2) の大きさの上限は status に当てない（E1）。
  - why: A2 は --force を持たない status の扱いを決めていなかった。status は中身を比べるだけで差分の本文を作らないので、全体をメモリに持たずに比べられ、上限で読めないファイルを作る理由がない。
  - decided_by: 利用者（2026-10-05、詳細 E1 を推奨どおり採用）
- A13 --ref を使い --force のないファイル全体の merge で、読み込み元と書き込み先にあり参照先にないファイルは、書き込み先が変わっていないことを確かめられないので、書かずに failed に出す（E2）。
  - why: [A9](#A9) の三者の存在の組み合わせのうち、この組だけが決まっていなかった。参照先にないので書き込み先の変更の有無が分からず、上書きしない安全な側に倒す。--force を付ければ書ける。failed に出す error の文言は [A16](#A16) で実装者に委ねた。
  - decided_by: 利用者（2026-10-05、詳細 E2 を推奨どおり採用）
- A14 status は、[A5](#A5) の読めないファイルを diff と同じく JSON ではトップレベルの errors に path と reason を持つ項目で出し、summary にその件数を出す。テキストでは標準エラーか今のエラーの出し方で示す（E3）。
  - why: A5 は status の files に載せるかと summary での数え方を決めていなかった。diff と同じ形にすると、JSON を読む側が両方のコマンドを同じに扱える。summary の件数のキー名とテキストの文言は [A16](#A16) で実装者に委ねた。
  - decided_by: 利用者（2026-10-05、詳細 E3 を推奨どおり採用）
- A15 diff の走査が件数の上限を超えたとき、[A4](#A4) で errors に載せる理由は、[REQ-scan-008](../../ir/scan/limits.md#REQ-scan-008) の上限の超過を案内する文とする（E6）。
  - why: A4 は上限の超過を errors に載せることだけを決め、理由の文を決めていなかった。既存の案内の文を使えば、上限の上げ方とパスの指定の仕方が利用者に伝わる。
