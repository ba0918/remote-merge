# 接続とエージェントの配置・書き込みの安全の穴を塞ぐ判断

## Context

レビューで、Agent が既存の symlink のリンク先を書き換えること、別の鍵種別でだけ known_hosts に登録されたホストの鍵や承認後の再接続の鍵を確認なしに信頼すること、他人が置き換えられる配置先の Agent のバイナリを実行することが見つかった。
IR は未知のホスト鍵の扱い（[REQ-ssh-001](../../ir/ssh/host-key.md#REQ-ssh-001)、[REQ-ssh-002](../../ir/ssh/host-key.md#REQ-ssh-002)）と Agent を使えないときの扱い（[REQ-ssh-005](../../ir/ssh/fallback.md#REQ-ssh-005)、[REQ-ssh-009](../../ir/ssh/sudo.md#REQ-ssh-009)）しか定めておらず、known_hosts を読めないとき、失効とされた鍵、Agent の配置先の検査を決めていない。
ここでその規則を決め、既存の要件から導かれる選択とあわせて残す。
[A31（Agent の方式とデプロイ手順を IR に含めない）](./2026-09-25-spec-migration.md#A31) は転送の方式と通信の版を利用者の契約から外す決定である。A3・A4 は方式によらず利用者の SSH のセッションで何を実行しないかを定める安全の制約で、配置の手順を契約にするものではないため、A31 の対象の外として IR に書く。

## Agreements

- A1 known_hosts がないこと以外の理由で known_hosts を読めないとき（UTF-8 として不正な内容、読む権限がないなど）、接続を止め、--yes や strict_host_key_checking=no を指定していても未知のホストとして扱わない。
  - why: 読み込みの失敗を「ファイルがない」と同じにすると、鍵が変わったホストが未知のホストになり、--yes で受け入れられてしまう。
  - decided_by: 利用者（2026-10-05、計画の承認による）
- A2 known_hosts で "@revoked" として失効とされた鍵は、--yes や strict_host_key_checking=no を指定していても受け入れず、接続を止める。対象は今の照合が一致と判定するホストの書き方（平文、カンマ区切り、ハッシュ形式）の行だけで、"*" などのワイルドカードは今の照合と同じく扱わない。同じ鍵が通常の行にもあるときは失効を優先する。
  - why: 失効の印は利用者がその鍵を信頼しないと明示したもので、自動承認の指定で覆すと失効の意味がなくなる。
  - decided_by: 利用者（2026-10-05、計画の承認による）
- A3 Agent の配置先のディレクトリがなければ所有者だけが読み書き・実行できるモード 700 で作る（sudo=true では既存の配置のコマンドと同じく sudo で作る）。配置先のディレクトリが symlink であるとき、所有者が SSH のセッションの "id -u"（sudo=true では 0、つまり root）でないとき、グループかその他が書き込めるときは、版の確認を含めてその中のものを何も実行せず、Agent を起動できない既存の扱いに乗せる（sudo=false では SSH の経路で続け、sudo=true では止まる）。所有者は設定のユーザー名とは比べない。
  - why: 他人が書き込める場所や他人の持ち物の中のバイナリを実行すると、他人の用意したプログラムが利用者の権限で動く。版の確認もそのバイナリを実行するので、検査はそれより前に置く。設定のユーザー名とログイン後の uid は一致するとは限らないため、実際に動くセッションの uid と比べる。
  - decided_by: 利用者（2026-10-05、計画の承認による）
- A4 配置先のバイナリの版が一致しても、ローカルの Agent のバイナリを解決できたときはそれと SHA-256 を照合し、一致しないとき、またはリモートでハッシュを計算できないときは、置かれたバイナリを実行せず版が違うときと同じ配置の経路で置き直す。ローカルのバイナリを解決できないとき（リモートのターゲット用のバイナリが手元にない、大きさの上限を超えるなど）は照合できないので、A3 の検査を通ったことだけを根拠に今までどおり実行する。拒否したときは A3 と同じく Agent を起動できない既存の扱いに乗せ、新しい文言や終了コードは決めない。
  - why: 版の出力は偽装できるので、版の一致だけでは置かれたバイナリが手元のものと同じだと言えない。解決できないときに実行を止めると、利用者が手で置いた Agent が使えなくなる。
  - decided_by: 利用者（2026-10-05、計画の承認による）
- A5 同じホストが known_hosts に別の鍵種別でだけ登録されているとき、提示された鍵は known_hosts で確かめられていないので、未知の鍵として扱う。strict_host_key_checking=yes や確認の手段がないときは止まり、--yes や strict_host_key_checking=no では承認できる。
  - why: [REQ-ssh-001](../../ir/ssh/host-key.md#REQ-ssh-001) は確かめられていない鍵を無確認で信頼することを禁じ、[REQ-ssh-002](../../ir/ssh/host-key.md#REQ-ssh-002) は明示した自動承認を認める。別の種別の登録は提示された鍵を確かめる材料にならないので、未知の鍵の扱いがそのまま当てはまる。拒否にすると、正しく鍵を追加したい利用者が承認する道もなくなる。
  - rejected: 別の種別でだけ登録されたホストの鍵を常に拒否する案は、既存の要件にない拒否を足すため採らない。
  - decided_by: 利用者（2026-10-05、計画の承認による）
- A6 Agent は、最後の要素が既存の symlink であるパスへ通常ファイルを書かずエラーにし、リンクもリンク先も変えない。symlink の作り直しはリンクそのものを消して作り、リンク先を消さない。そのエラーで製品側が Agent を使えないものとして扱い、sudo=false では SSH の経路へ移り、sudo=true では止まる既存の扱いを受け入れる。
  - why: リンクを通常ファイルに置き換えるのは [REQ-merge-001](../../ir/merge/symlink.md#REQ-merge-001) が禁じる種類の変更で、リンク先へ書くのは書き込み先の外を変える。残る選択はエラーだけである。symlink の作り直しは [REQ-merge-003](../../ir/merge/symlink.md#REQ-merge-003) のとおりリンクそのものに行う。SSH の経路の書き込みが symlink を辿る問題は別に扱う。
  - decided_by: 利用者（2026-10-05、計画の承認による）
