# 変異テストで流すテストを絞る判断

## Context

CLI diff の差分の出し方のテスト整理で、変異テストが 1 件に約 29 秒（ビルド約 13 秒、全テスト 3,061 件の実行約 17 秒）かかり、230 件で約 2 時間になった。テストの実行が全コアを使うため CPU が張り付き、利用者の PC が重くなって途中で止めた。
CPU の割り当てを絞るだけでは 2 時間がさらに延びるため、利用者は受け入れなかった。
試しに変異 5 件で、流すテストを絞り、デバッグ情報を切り、テストの並列数を抑えて回し、結果と時間を前の全テストでの実行と比べた。その結果をもとに "scripts/mutants.sh" の既定を決める。
利用者は、絞ったことで重要なものがテストされなくなることを懸念した。

## Agreements

- A1 "scripts/mutants.sh" は変異ごとに流すテストを、単体テスト（cargo の --lib）と、kotowari が根拠に数えるテスト（tests.files に挙げた "tests/contract" と "tests/cli_diff.rs"）に限る。
  - why: 流すテストを減らしても結果は caught から見逃しの方向にしか変わらず、見逃しは [REQ-testing-012](../../ir/testing/methods.md#REQ-testing-012) で一件ずつ決着させるため、テストされていないものが見えなくなることはない。範囲外の TUI の結合テストは負荷で落ちることがあり、試しでは src/cli/diff.rs:174:74 を前の実行で caught にしていたのが tui_merge の test_merge_cancel_with_n の失敗だけで、絞ると見逃しになった（記録では既に FLAG-cli-038 の範囲として扱っていた）。他の 4 件は前と同じ結果で、落としたテストも同じだった。
  - decided_by: 利用者（推奨を採用）
- A2 "scripts/mutants.sh" は変異テストのビルドをデバッグ情報なしで行う。
  - why: 変異ごとのビルドはテストの実行ファイルのリンクが大半を占め、試しでは流すテストを絞ったことと合わせて 1 件のビルドが約 13 秒から約 5 秒になった。デバッグ情報は変異の検知に使わない。
  - decided_by: 利用者（推奨を採用）
- A3 "scripts/mutants.sh" は同時に走らせるテストの数を 3 に抑える。
  - why: 試しの 5 件で、上限なしは 170 秒・平均約 3.9 コアでテストの間は全コアに張り付き、3 では 234 秒・平均約 2.7 コアだった。PC が重くなったことが発端のため、速さより負荷の低さを取る。どちらも前の設定（全テスト、5 件で約 5.6 分）より速い。試しの間には別のプロジェクトのビルドが重なっており、時間には誤差がある。
  - rejected: 上限なし。最も速いが、テストの間は CPU が張り付く。
  - decided_by: 利用者（推奨を採用）

## Rejected

- R1 流すテストはそのままにし、サービスの CPU の割り当て（CPUQuota）だけを絞る。
  - why: 負荷は下がるが 1 回が 2 時間よりさらに延び、利用者が「毎回 2 時間は話にならない」として受け入れなかった。
  - decided_by: 利用者
