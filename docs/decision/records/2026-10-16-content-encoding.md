# ファイル内容の文字コード対応

## Context

レガシーサーバの EUC-JP のファイルを diff するとバイナリとされ、利用者が scp で取得して比較し直す事例があった。
現行の [REQ-cli-061](../../ir/cli/binary.md#REQ-cli-061) は非 UTF-8 をバイナリとするため、実装だけでなく仕様の変更が要る。
調査では、差分表示、競合判定、部分マージが別々に UTF-8 を解釈し、部分マージ結果は UTF-8 のバイト列で書かれることを確認した。
利用者は、内容の解釈を共通化し、転送と保存のバイト列を保持する方針を承認した。
特に、共通化の漏れが将来の実装の不整合につながらない構造を求めている。

Position: 仕様の境界事例は確定し、実装は未変更。次の工程は仕様の最終承認と、その仕様に基づく実装計画。

## Agreements

- A1 初期対応は UTF-8、EUC-JP、Shift_JIS 系の明示指定とする。Shift_JIS 系のマッピングは未決事項 U1 で定める。
  - why: 必要な文字コードを指定して比較できれば、今回の手動取得をなくせる。自動推定の曖昧さを初期対応の必須条件にしない。
  - decided_by: 利用者（提示した設計方針を承認）
- A2 ファイル内容の正本は元のバイト列とし、ハッシュ、一致判定、更新検知、全体 merge と sync、バックアップ、rollback の既存の意味を変えない。
  - why: デコードした文字が同じでも異なるバイト列があり、文字としての一致で更新確認を代用すると変更を見逃す。
  - decided_by: 利用者（提示した設計方針を承認）
- A3 差分表示、参照先との差分、行単位の競合判定、部分マージに、同じ文字コード選択、デコード、行分割、hunk の区切りを適用する。
  - why: diff で見た hunk 番号と実際に適用する変更を一致させ、参照先だけ別の解釈になることを防ぐ。
  - decided_by: 利用者（提示した設計方針を承認）
- A4 文字コードは接続先と root_dir からの相対パスで選び、CLI の側ごとの上書き、接続先とパスのルール、接続先の既定値、未設定時の現行動作の順に優先する。左右と参照先に同じ規則を適用する。
  - why: 同じサーバに文字コードの異なるファイルが混在し、ローカルかリモートかだけでは必要な解釈を決められない。
  - decided_by: 利用者（提示した設計方針を承認）
- A5 初期対応の部分マージは読み込み元と書き込み先が同じ文字コードの場合に限り、選んだ変更に読み込み元のバイトを使い、選ばなかった箇所に書き込み先のバイトを残す。改行と末尾改行の有無も勝手に正規化しない。
  - why: 全文を再エンコードすると、選ばなかった箇所のバイトまで変わる可能性がある。
  - decided_by: 利用者（提示した設計方針を承認）
- A6 デコードに失敗した内容を置換文字で比較や部分マージに使わず、読めない理由を示す。参照先を解釈できないことを競合なしとして扱わない。
  - why: 情報を失った文字列からの比較や書き込みでは、利用者の指定していない変更を起こしうる。
  - decided_by: 利用者（提示した設計方針を承認）
- A7 文字として同じでも元のバイト列が違うファイルは差分ありとし、行の変更がない表現上の差であることを示す。
  - why: 空の hunks だけでは、差分ありの判定と表示が食い違って見える。
  - decided_by: 利用者（提示した設計方針を承認）
- A8 文字コードの内容設定は SSH 接続の設定から分離する。ファイル名、パス、symlink のリンク文字列の UTF-8 制約と Agent の通信形式は変更しない。
  - why: 今回必要なのは取得済みの内容の解釈であり、接続や名前の契約を変える必要がない。
  - decided_by: 利用者（提示した設計方針を承認）
- A9 文字コード選択、内容の適格性判定、行の表現と hunk の構築は共通の入口に集約し、呼び出し側が個別に再判定する構造にしない。この構造の決定自体は IR にせず、利用者に見える結果の一致を IR にする。
  - why: 利用者が特に共通化の漏れによる将来の不整合を懸念している。内部の配置は利用者に見える動作ではなく、実装計画とコードの型や依存関係で守る。
  - decided_by: 利用者（「特に共通化すべきものがされてないと、今後見落として整合性の撮れてない実装を生み出します」）
- A10 Shift_JIS 系には encoding_rs の CP932／Windows-31J 相当のマッピングを採用し、shift_jis、cp932、windows-31j を同じ指定として受け付ける。厳密な JIS 版との違いを利用手引きに明記する。
  - why: 利用者が Windows の拡張文字も扱う推奨案を選択した。
  - decided_by: 利用者（第 1 ラウンド Q1 で推奨を採用）
- A11 UTF-8 の先頭の BOM は行の本文から分離し、部分マージでは書き込み先の BOM の有無を保つ。BOM だけの違いは行の差でなく表現上の差とし、全体コピーは読み込み元の全バイトを転送する。
  - why: 最初の行の変更を選ぶことで、書き込み先の BOM が意図せず増減することを防ぐ。
  - decided_by: 利用者（第 1 ラウンド Q3 で推奨を採用）
- A12 内容設定はグローバルとプロジェクトの二層を合成する。接続先ごとの既定値はプロジェクトにあるキーを優先し、パスルールはグローバルの後にプロジェクトの順で連結して最後の一致を優先する。パスルールはどのスコープでも既定値より優先し、CLI の側ごとの指定は全ルールより優先する。
  - why: 共通のパスルールを再記述せず継承し、プロジェクト側で必要な例外だけ上書きする。利用者が二層の合成を提案し、グローバルのパスルールとプロジェクトの既定値の組み合わせも具体例で承認した。
  - decided_by: 利用者（第 2 ラウンド Q2 で合成方式を選択）
- A13 明示した文字コードでデコードできない場合、diff はパス、側、文字コードと理由を示して終了コード 2 を返し、他のファイルの diff は続ける。部分マージは書かずに止め、--force でも不正なデコードを使用しない。未設定の非 UTF-8 と先頭 8,192 バイトに NUL がある内容は従来どおりバイナリとする。
  - why: 誤った設定や不正な内容をバイナリ扱いで隠さず、情報を失う変換で書き込むことを防ぐ。
  - decided_by: 利用者（第 3 ラウンド Q4 で推奨を採用）
- A14 部分マージで存在しない側には文字コードを持たせず、存在する側の文字コードで空の内容として比べる。新規作成する書き込み先の文字コードと BOM は読み込み元から引き継ぐ。存在しない書き込み先の設定が別の文字コードでも自動変換しない。
  - why: 存在しないことと空ファイルを区別し、元のバイトを使う部分マージを片側だけのファイルでも成立させる。
  - decided_by: 利用者（第 3 ラウンド Q5 で推奨を採用）
- A15 全体コピーが文字コード変換を行わないことをヘルプと dry-run で示す。
  - why: 内容を読むための文字コード設定を、書き込み先の文字コードへ変換する指定と誤解させない。
  - decided_by: 利用者（第 3 ラウンド Q6 の条件を承認）
- A16 左右と参照先の既存の内容を指定した文字コードでテキストとして解釈できるときは、文字コードが互いに異なっても行の変更から競合を求める。バイナリの競合と存在の組み合わせによる競合は既存のファイル全体の規則を保ち、明示指定のデコード失敗は競合なしに置き換えずエラーとする。
  - why: A3 と A6 の共通の解釈を三者比較にも適用し、UTF-8 でないことだけを理由にファイル全体の競合へ切り替える旧来の制約を除く。
  - decided_by: 利用者（提示した三者比較の設計方針と第 3 ラウンド Q4 を承認）
- A17 行の比較には LF と CRLF の違いと末尾改行の有無を含める。差分表示、参照先との差、競合判定、部分マージの全てに同じ規則を使い、BOM だけを本文から分ける。
  - why: 改行だけの変更を行の変更として選べるようにし、用途によって変更や競合が消えないようにする。
  - decided_by: 利用者（第 4 ラウンド Q7 で推奨を採用）
- A18 三者のどれかがバイナリなら競合は元バイトによるファイル全体の比較で決め、左右の両方が参照先から変わり左右も異なる場合を一つの競合とする。その競合があれば部分マージは --dry-run でも書き込まず止まる。--force は参照先の競合確認を省略できるが、左右のデコード失敗や異なる文字コード間の部分マージの制約を回避しない。
  - why: バイナリの参照先を行の変更なしと扱う誤りを防ぎ、diff と部分マージで同じ競合結果を使う。
  - decided_by: 利用者（第 4 ラウンド Q8 で推奨を採用）
- A19 デコード失敗の diff は既存の読み込み失敗と同じ出力範囲にする。左右のどちらかの失敗ならファイル項目と差分件数から外し、参照先だけの失敗なら左右の差分を残して参照先との差と競合結果を出さない。いずれも JSON のトップレベルの errors にパスを出し、理由に側と文字コードを含め、終了コード 2 を返す。
  - why: 読めなかった内容を空と扱わず、参照先だけの失敗で比較できた左右の差分まで失わない。
  - decided_by: 利用者（第 4 ラウンド Q9 で推奨を採用）

## Delegated

- D1 内容設定の具体的なキー、CLI の引数名、追加する JSON 欄の名前を実装へ委任する。既存の形式を壊さず、合意した選択規則と失敗条件を変えずに、利用手引きとテストを一致させる範囲に限る。
  - why: いずれの表記でも承認済みの動作は同じであり、既存の型と出力形式を読んで表記を選ぶ方が不要な重複を避けられる。
  - decided_by: 利用者（第 3 ラウンド Q6 で表記の委任を選択）
- D2 内容設定は [content.defaults] の接続先名をキーとする文字コード指定と、[[content.rules]] の side、path、encoding で表す。side は local または設定のサーバ名とする。path は既存の exclude と同じパターンの照合方法を使う。文字コード名は大文字小文字を区別せず utf-8、euc-jp、shift_jis、cp932、windows-31j と、テキスト解釈をしない binary を受け付け、他の名前や不明な接続先は設定エラーとする。
  - why: D1 の委任により、接続設定を変更せず内容だけを設定できる表記を選んだ。既存のパターン照合を使い、文字コードルールだけ別の glob の意味になることを避ける。
  - decided_by: AI（D1 の表記の委任に基づく）
- D3 CLI の diff と merge の上書き指定には --left-encoding、--right-encoding、--ref-encoding を使う。diff の JSON のファイル項目には encodings に left、right、ref の使用文字コードを入れ、存在しない側を省く。文字コード名は utf-8、euc-jp、shift_jis に正規化する。元バイトだけが違うときは byte_only_difference を true として元バイトのハッシュと note を示す。これらは追加の欄とし既存の欄の意味を変更しない。
  - why: D1 の委任により、既存の左右と参照先の名前を使う表記を選んだ。表現上の差を note の文章だけに依存せず機械でも区別できるようにする。
  - decided_by: AI（D1 の表記の委任に基づく）

## Prohibitions

- P1 初期対応には自動文字コード推定と、異なる文字コード間の部分マージを含めない。
  - why: 推定の曖昧さと取り込む文字の変換失敗を初期対応から切り離し、明示指定と同一文字コードの安全な部分マージを先に成立させる。
  - decided_by: 利用者（提示した設計方針を承認）
- P2 全体 merge と sync で書き込み先の文字コードへの自動変換を行わない。
  - why: 既存の元バイト列を転送する契約を維持する。文字コード変換を加えると複数の書き込み先への計画と失敗の意味も変わる。
  - decided_by: 利用者（提示した設計方針を承認）
