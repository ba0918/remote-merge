# --format json の出力を一行の JSON にする

## Context

--format json の出力は、serde_json の to_string_pretty で二つの空白で字下げした複数行になっていて（crates/remote-merge/src/service/output.rs の format_json と、crates/remote-merge/src/main.rs の handle_with_format）、AI が CLI を呼ぶたびに空白の分も読んでいた。
一行にすると、手引きの例 10 個で 4,580 バイトが 2,976 バイトに、3 ファイル × 3 hunk × 20 行の試しの diff で 21,774 バイトが 10,281 バイトに減る（バイト数で測った。トークン数は測っていない）。
[REQ-cli-018](../../ir/cli/results.md#REQ-cli-018) は JSON として解釈できることだけを約束していて、整形するかどうかは書いていなかった。
利用者は、引き継ぎメモの「振る舞いを変える提案」のうち、この一行の JSON にする案を選んだ。この記録は、出力の形と、それを仕様にどう書くかを決めたものである。

Position: 問いを出し尽くし、[REQ-cli-102](../../ir/cli/results.md#REQ-cli-102) を足して、REQ-cli-018 に logs の場合と引数の解析で止まる場合を書き足した。利用者が承認し、この仕様のとおりに実装した。実装の後の仕様との突き合わせで、REQ-cli-018 に --help と --version の場合の文が足された（[2026-10-24-json-one-line-consistency.md](./2026-10-24-json-one-line-consistency.md) と [2026-10-24-json-one-line-consistency-2.md](./2026-10-24-json-one-line-consistency-2.md)）。

## Agreements

- A1 --format json の status・diff・merge・sync・rollback の結果と、失敗のときのエラーの JSON を、すべて一行の JSON で出す。logs の、記録一件ごとに一行の JSON を出す今の出し方は変えない。
  - why: --format json の出力の形が、どのコマンドでもそろう。logs は crates/remote-merge/src/cli/logs.rs が serde_json の to_string で一件ずつ出していて、すでにこの形をしている。結果には、部分成功などで終了コード 2 を返すときの結果も含む。JSON は標準出力に出すもので、標準エラーに出す確認の行や警告はこの決定の外にある。--help を付けたときに標準出力に出る使い方は、結果でもエラーでもないので含まない（この三点は、仕様の見直しで AI が導き、要件の文の「終了コードによらず」「標準出力」「結果かエラーの JSON を出すとき」という条件として書いた。利用者には見直しの回の一覧で示した）。
  - rejected: diff だけ一行にする（コマンドによって、一行の JSON と複数行の JSON が混ざる）。
  - decided_by: 利用者（推奨を採った）
- A2 一行の JSON には、文字列の外に空白を入れない。「:」と「,」の後にも入れない（serde_json の to_string の形）。
  - why: いちばん短く、serde_json の標準の一行の書き方をそのまま使える。serde_json の to_string は文字列の外に空白・タブ・CR・LF のどれも入れないので、ここでいう空白はその四つを指す。失敗のときに JSON を作れなかった場合に出す固定の文言（main.rs の handle_with_format の {"error": "internal serialization error"}）も失敗のときの JSON なので、この形に含まれる（AI の読み）。
  - rejected: 「:」と「,」の後に空白を入れる（バイトが増え、書き方を自分で用意して保つことになる）。
  - decided_by: 利用者（推奨を採った）
- A3 一行の JSON の後に、改行（LF）を一つ付ける。
  - why: 今と同じで、シェルの read や head -n 1 のような行で読む道具が、そのまま一件として読める。
  - rejected: 付けない（行で読む道具によっては、最後の行が欠けて見えたり、次のプロンプトが同じ行に続いたりする）。
  - decided_by: 利用者（推奨を採った）
- A4 「一行」は、JSON の途中に LF がなく、最後に LF が一つだけあることをいう。文字列の中の U+2028・U+2029・U+0085 は書き換えずにそのまま出す。
  - why: serde_json の to_string は（Cargo.lock が使う 1.0.154 と、Cargo.toml の下限の 1.0.149 の両方で試した）、文字列の中の制御文字（U+0000〜U+001F。LF と CR を含む）を "\n"・"\r"・"\u000b" のように書き、U+2028・U+2029・U+0085 はそのまま出す（試して確かめた）。JSON の決まりでは、どちらも正しい。シェルの read・head や jq など、行で読む多くの道具は LF だけで行を分ける。diff はファイルの中身を載せるので、中身にこれらの文字があれば出力にも入る。
  - rejected: U+2028・U+2029・U+0085 も "\u2028" のように書き換える（書き換えの仕組みを自分で用意して保つことになり、効くのは Python の str.splitlines() のように、これらの文字でも行を分ける道具だけである）。
  - decided_by: 利用者（推奨を採った）
- A5 logs --format json の、記録一件ごとに一行の JSON を出す今の出し方も、一行の約束として仕様に書く。logs の出力は変えない。
  - why: 仕様の約束にすると、後で崩れたときにテストで気づける。これまで、この出し方はどの要件にも書かれていなかった。今の出し方では、失敗したときは記録の行を出さず、エラーの JSON だけを出す（そのエラーの JSON は今は複数行で、[A1](#A1) で一行になる）。crates/remote-merge/src/cli/logs.rs の run_logs は、水準と --since の確かめと記録の読み込みを、一行目を出す前にすべて終え、そこで失敗すれば何も出さずにエラーを返すからである（この点は、仕様の照合の後に AI が今の作りを読んで書き足し、要件の「エラーの JSON を出すときはその一行だけ」の根拠にした）。
  - rejected: 書かない（仕様の約束でないと、変わってもテストで気づけない）。
  - decided_by: 利用者（推奨を採った）
- A6 一行で出す約束は、[REQ-cli-018](../../ir/cli/results.md#REQ-cli-018) の隣に新しい要件 [REQ-cli-102](../../ir/cli/results.md#REQ-cli-102) として足し、REQ-cli-018 の文に一行の約束は書き足さない。
  - why: 「JSON を返す」と「一行で返す」を別の約束として持ち、それぞれにテストを付ける。この問いで決めたのは一行の約束の置き場所で、REQ-cli-018 に別の理由で書き足すこと（[A7](#A7)）を妨げるものではない。
  - rejected: REQ-cli-018 の文に書き足す（二つの約束が一つの要件に混ざる）。
  - decided_by: 利用者（仮決めの推奨を承認した）
- A7 --level・--since・--tail で絞った後に一件も記録が残らない logs --format json は、今のまま標準出力に何も出さず、終了コード 0 で終わる。[REQ-cli-018](../../ir/cli/results.md#REQ-cli-018) に「logs は絞った後に残った記録を一件ずつ JSON として返し、残った記録がなければ標準出力に何も出さずに終了コード 0 で終わる」と書き足す。
  - why: REQ-cli-018 は、成功とエラーのどちらでも JSON として解釈できる結果を返すと書き、例外には確認を断った取り消しだけを挙げていた。空の出力は JSON として解釈できず、記録が二件以上あるときも出力の全体は一つの JSON ではないので、REQ-cli-018 の字面と logs の今の出し方は合っていなかった（REQ-cli-018 のテストは logs を見ていない）。[A5](#A5) で logs の出し方を仕様に書くと、この食い違いが仕様の中に現れるので、REQ-cli-018 の側に logs の場合を書く。記録のない logs が標準出力に何も出さず終了コード 0 で終わることは、手元にあった 2026-10-23 のビルドを、診断ログの置き場を空の一時ディレクトリに向けて動かして確かめた。最初は「記録が一件もない」場合として決め、仕様の見直しで、絞って一件も残らない場合も同じ扱い（今のまま）だと書き足した。こちらも同じビルドで、INFO の記録を一件だけ置いて --level error で動かし、標準出力と標準エラーに何も出さず終了コード 0 で終わることを確かめた。
  - rejected: REQ-cli-018 は変えず、新しい要件の側にだけ logs の形を書く（REQ-cli-018 だけを読むと、記録のない logs も JSON を出すように読め、仕様の中に食い違いが残る）。
  - decided_by: 利用者（推奨を採った）
- A8 この題で変えるのは、--format json の出力の空白と改行だけとする。欄の名前・順・中身は変えない。
  - why: 一つのブランチで小さく入れられる。ほかのトークン削減の提案は欄の形か中身を変えるので、別に決める。
  - rejected: ほかのトークン削減の提案もこの題に含める（問いが大きく増え、一つの変更も大きくなる）。
  - decided_by: 利用者（推奨を採った）
- A9 手引き（skills/remote-merge の SKILL.md と references/json-schemas.md）の JSON の例は整形したまま残し、実際の出力は一行だと一文足す。これは仕様（IR）ではない。
  - why: 例は欄の形を見せるためのもので、読みやすさを優先する。手引きは振る舞いを説明する文書で、このプロジェクトは手引きを kotowari のガイドとして扱っていない（.kotowari/config.yaml の guides.files が空）。振る舞いそのものは REQ-cli-102 に書く。
  - rejected: 例も一行に書き直す（例の欄が読みにくくなる）。
  - decided_by: 利用者（仮決めの推奨を承認した）
- A10 CHANGELOG の [Unreleased] の「変更（互換性に注意）」に、この変更を書く。これは仕様（IR）ではない。
  - why: JSON の中身は同じで形だけが変わり、JSON として読む使い方には影響しない。整形された形を、行ごとや字下げを頼りに読んでいた使い方は動かなくなる。CHANGELOG はリリースの記録で、使う人が見る振る舞いそのものは REQ-cli-102 に書く。
  - rejected: 「変更（互換性がないもの）」に書く（JSON の中身は同じで、形だけが変わる変更だから）。
  - decided_by: 利用者（仮決めの推奨を承認した）
- A11 引数の解析で止まったとき（必須の引数がない、値の形が合わない）は、--format json でも JSON を出さず、終了コード 2 で終わる。これを [REQ-cli-018](../../ir/cli/results.md#REQ-cli-018) に書き足す。
  - why: 引数を読む部品（clap）が止めるので、JSON でエラーを出す処理（crates/remote-merge/src/main.rs の handle_with_format）まで届かない。手元にあった 2026-10-23 のビルドで、logs --format json --tail abc と、パスのない merge --format json が、どちらも標準出力に何も出さず、標準エラーに clap の "error: ..." を出して終了コード 2 で終わることを確かめた。REQ-cli-018 は成功とエラーのどちらでも JSON を返すと書き、merge と sync の指定のエラーの表（[TBL-cli-008](../../ir/cli/merge.md#TBL-cli-008)・[TBL-cli-006](../../ir/cli/sync.md#TBL-cli-006)）はパスがないときを「引数の解析エラー」としていたので、前から REQ-cli-018 の字面と合っていなかった。仕様の見直しで見つかった。今の振る舞いを書くので、振る舞いは変わらない。
  - rejected: この題では直さず FLAG に残す（仕様が食い違いを抱えたまま進む）。引数の解析で止まったときもエラーの JSON を出すように変える（振る舞いが変わり、[A8](#A8) の範囲を超える）。
  - decided_by: 利用者（推奨を採った）

## Prohibitions

- P1 整形した JSON を出す指定は作らない。--format json-pretty のような別の値も、端末に出すときだけ整形することもしない。
  - why: 指定・仕様・テストが増え、人が読むときは jq などで整形すれば足りる。端末に出すときだけ整形すると、AI が擬似端末の中で動かしたときに節約が効かないことがある。古い版を使っている利用者はいない。
  - rejected: --format json-pretty を足す。端末に出すときだけ整形する。
  - decided_by: 利用者（推奨を採った）
- P2 この題では、欄の名前・順・中身を変えるトークン削減の提案を扱わない。比べる先の情報を一度だけ置く、copy_note を一度だけにする、ほかの欄から求まる欄やいつも同じ値の欄を省く、diff の行を文字列にする、route_choice の理由を短くする、の五つで、残課題に残す。
  - why: [A8](#A8) のとおり、この題は空白と改行に限る。
  - decided_by: 利用者（推奨を採った）
- P3 この題では、sync の取り消しや rollback の中止が --format json で何も出さずに終了コード 0 で終わる件を見直さない。残課題に残す。
  - why: 出力の形ではなく何を出すかの判断で、[A8](#A8) の範囲の外にある。
  - decided_by: 利用者（推奨を採った）

## Rejected

- R1 diff だけ一行にする。
  - why: コマンドによって、一行の JSON と複数行の JSON が混ざる。
- R2 「:」と「,」の後に空白を入れる。
  - why: バイトが増え、書き方を自分で用意して保つことになる。
- R3 一行の JSON の後に改行を付けない。
  - why: 行で読む道具によっては、最後の行が欠けて見えたり、次のプロンプトが同じ行に続いたりする。
- R4 --format json-pretty のような別の値を足す。
  - why: 指定・仕様・テストが増える。整形は jq で足りる。
- R5 端末に出すときだけ整形する。
  - why: 出し先で出力が変わり、AI が擬似端末の中で動かすと節約が効かないことがある。
- R6 手引きの例も一行に書き直す。
  - why: 例の欄が読みにくくなる。
- R7 ほかのトークン削減の提案もこの題に含める。
  - why: 問いが大きく増え、一つの変更も大きくなる。
- R8 U+2028・U+2029・U+0085 も "\u2028" のように書き換える。
  - why: 書き換えの仕組みを自分で用意して保つことになる。行で読む道具の多くは LF だけで行を分ける。
- R9 logs の一件一行は仕様に書かない。
  - why: 仕様の約束でないと、変わってもテストで気づけない。
- R10 一行の約束を REQ-cli-018 の文に書き足す。
  - why: 「JSON を返す」と「一行で返す」が一つの要件に混ざる。
- R11 CHANGELOG の「変更（互換性がないもの）」に書く。
  - why: JSON の中身は同じで、形だけが変わる変更だから。
- R12 REQ-cli-018 は変えず、新しい要件の側にだけ logs の形を書く。
  - why: REQ-cli-018 だけを読むと、記録のない logs も JSON を出すように読め、仕様の中に食い違いが残る。
- R13 引数の解析で止まったときに JSON を出さない件を、この題では直さず FLAG に残す。
  - why: 仕様が食い違いを抱えたまま進み、今の振る舞いを書くだけで解ける。
- R14 引数の解析で止まったときも、エラーの JSON を出すように変える。
  - why: 振る舞いが変わり、空白と改行だけというこの題の範囲を超える。

  - why: どこに置いても、例は整形のまま読めて、実際の出力が一行だと手引きから分かるという [A9](#A9) の結果は変わらない。
  - decided_by: 利用者（結果の画面で承認した）
