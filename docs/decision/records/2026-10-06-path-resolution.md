# どの経路でも同じ手順でパスを辿る

## Context

rollback の書き戻す前のパスの確認は、ローカルは `std::fs::canonicalize`（glibc の realpath）と Rust の `Path::parent()`、エージェントも同じ Rust の手順、SSH はそれを POSIX sh で真似たスクリプトで行っている。
SSH のスクリプトをローカルに合わせる修正を三回重ねたが、そのたびに PATH_MAX の付近や連なった symlink で新しい経路差か退行が見つかった（path-validation の findings 15〜17）。
カーネルと realpath と `Path::parent()` の振る舞いをシェルで再現する方式は収束しないと判断し、利用者は 2026-10-06 に、どの経路も同じ明示した手順（要素ごとの lstat・readlink・ディレクトリかの判定）でパスを辿り、長さの上限・辿る回数の上限・ファイルに付いた末尾の "/" の扱いを IR に書く形に作り直すと決めた（このブランチで行い、ローカルとエージェントの振る舞いも変わってよい）。

Position: 差分レビューの後で A58・A59 が決まった。修正に回す。

## Agreements

- A1 パスの確認は、ローカル・SSH・エージェントのどの経路でも同じ明示した手順で要素ごとに辿る形に作り直し、カーネル・realpath・`Path::parent()` の振る舞いを SSH で再現する方式はやめる。この作業は path-validation のブランチで行い、ローカルとエージェントの振る舞いが変わってもよい。
  - why: 再現する方式は三回の修正のたびに新しい経路差か退行を生み、収束しなかった。同じ手順を同じ基本操作で書けば、経路差の生まれる余地は基本操作の違いだけになる。
  - rejected: 今の方式で四回目の修正を回す（収束の見込みが低い）。15〜17 を残したままマージし、作り直しを別の単位にする（退行を含めて取り込むことになり、このブランチの目的「三つの経路で同じ判定」を満たさない）。
  - decided_by: 利用者（2026-10-06、推奨を採った）
- A2 作り直す範囲はパスの確認（三つの経路のパスの確認と、rollback が使う祖先が通常ファイルかの判定）に限る。走査（`find -L`、WalkDir）、エージェントの root_dir の検証（validate_path）、書き込みの境界（O_NOFOLLOW）は範囲に含めない。
  - why: このブランチの目的は確認の結果を三つの経路でそろえることで、走査には REQ-config-033 などの別の要件と別の仕組みがあり、混ぜると範囲が倍になる。確認そのものは root_dir の中かを判定せず、その判定は呼び出し側に残る。
  - decided_by: 利用者（推奨を採った）

  - why: 上限に達する前に止めれば OS の ENAMETOOLONG に届かず、カーネルや realpath ごとの差が結果に出なくなる。

- A40 辿る手順と、ローカルとエージェントが使う標準ライブラリの基本操作（lstat・readlink・access(X_OK)）は、remote-merge-core の新しいモジュールに置く。core は Unix で libc に依存してよい。engine のローカルの確認とエージェントの確認はどちらもこの関数を呼び、確認の結果の型も core に置いて engine とエージェントの通信の型はそれに合わせる。
