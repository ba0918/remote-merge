# バックアップのローカル集約（移行元）

> kotowari IR への移行前の要件。実装済みの現行仕様としては扱わない。

## 1. 目的

マージ・sync・rollback などで上書き・削除する前に取るバックアップを、ローカルマシンの集約先 1 か所だけに保存する。
リモートサーバの root_dir 配下にも、ローカルのプロジェクトディレクトリにも、バックアップを作らない。
あわせて、rollback がどの書き込み先でも symlink を壊さないようにする。

背景: 現在のバックアップは書き込み先の root_dir 直下の `.remote-merge-backup/` に作られる。
root_dir が Web の公開ディレクトリの場合、`.env` などのバックアップを公開領域に平文で置くリスクが常に付きまとう。
また、サーバの数 × プロジェクトの数だけバックアップが分散する。

用語（「バックアップセッション」「書き込み先」）の定義は `CONTEXT.md` に従う。

## 2. 範囲

対象になる書き込みの経路:

- CLI: `merge`、`merge --hunks`、`merge --delete`、`sync`（`--delete` を含む）、`rollback`
- TUI: 1 ファイル単位のマージ、ディレクトリ単位のマージ、symlink のマージ、ハンクマージ（確定時にその場で書き込むもの）、ハンク適用後の `w`

どの経路でも、リモート → ローカル、ローカル → リモート、リモート → リモートの全方向を対象にする。

## 3. 要件

各要件の「成功条件」は外から観察できる結果、「反例」はその要件が満たされていない状態の例、「確認方法」は証拠の取り方を示す。
確認方法に出てくる「ローカルの書き込み先の結合テスト」は、一時ディレクトリをローカル・リモートの書き込み先の代わりに使い（3.20）、通常のテスト実行で走るテストを指す。
「リモートの E2E テスト」は、SSH でつなぐ `#[ignore]` 付きのテストを指し、testenv（CentOS 5 のコンテナ）に対してリリース前に実行する。

### 3.1 バックアップは集約先にだけ保存する

- 成功条件: 範囲内のどの経路・どの方向の書き込みでも、バックアップは集約先（3.2）にだけ作られる。
  書き込み先の root_dir 配下には、バックアップのためのファイルもディレクトリも作られない。
- 反例: develop へのマージの後、develop の root_dir に `.remote-merge-backup/` ができている。
  リモート → ローカルのマージの後、ローカルのプロジェクトディレクトリに `.remote-merge-backup/` ができている。
- 確認方法:
  - ローカルの書き込み先の結合テストで、マージ・sync・rollback の後に、root_dir 配下に書き込み対象以外の新しいファイルやディレクトリができていないことを確かめる。
  - リモートの E2E テストで、リモートの root_dir 配下に何も増えていないことを確かめる。
  - 既存の E2E テストのうち、リモートに `.remote-merge-backup/` ができることを確かめているもの（`tests/cli_merge.rs` など）は、この要件に合わせて置き換える。

### 3.2 集約先の場所

- 成功条件: 集約先は `$XDG_DATA_HOME/remote-merge/backups/`。`XDG_DATA_HOME` が未設定・空・相対パスのときは
  `~/.local/share/remote-merge/backups/`（XDG Base Directory の規約どおり、空や相対パスの値は未設定として扱う）。
- 反例: `XDG_DATA_HOME=/tmp/x` を設定して実行したのに、`~/.local/share/remote-merge/backups/` に保存される。
  `XDG_DATA_HOME=` と空で設定したら、カレントディレクトリ直下に `remote-merge/backups/` ができる。
- 確認方法: 集約先の場所を決める処理を、環境変数とホームディレクトリを引数で受け取る純粋関数にし、単体テストで確かめる。
- 集約先の場所が決まらない場合（ホームディレクトリが取得できない等）は 3.6 に従う。

### 3.3 集約先の権限

- 成功条件: 集約先とその中に作るディレクトリは所有者だけが読み書きできる（0700）。中に作るファイルは所有者だけが読み書きできる（0600）。
  元のファイルの権限はバックアップ側の権限に使わない。
- 反例: 権限 0644 の `.env` をバックアップした結果、集約先のファイルが 0644 になっている。
- 確認方法: ローカルの書き込み先の結合テストで、バックアップ後に集約先の中にあるすべてのディレクトリとファイルの権限を確かめる（中の構成には依存しない）。

### 3.4 バックアップの中身は上書き直前の内容と一致する

- 成功条件: 通常ファイルのバックアップの中身は、上書き（または削除）の直前に書き込み先のディスク上にあった内容とバイト単位で一致する。
  diff 表示のために以前読み込んだ内容は、バックアップの中身に使わない。
- 反例: diff を表示した後、書き込み前に別のプロセスが同じ秒のうちに書き込み先のファイルを書き換えた。
  その後マージすると、バックアップには diff 表示時点の古い中身が入っている。
- 確認方法: サービス層の結合テスト（ローカルの書き込み先）で、マージに必要な情報を組み立てた後、書き込みを実行する前に、
  書き込み先の中身を変えて更新日時を元に戻す。そのうえで書き込みを実行し、続けて rollback したときに戻る中身が、変更後の中身と一致することを確かめる。
  集約先の中の記録形式（8 章で実装に委ねたもの）は直接読まない。
- この要件は通常ファイルが対象。symlink は 3.10 に従う。

### 3.5 バックアップを取る対象

- 成功条件: TUI の `w` を除くすべての経路では、その操作で上書き・削除する書き込み先のファイルだけをバックアップする。
  読み込むだけの側はバックアップしない。
- 書き込み先に元のファイルが無い（新しく作る）場合は、何も記録しない。これはバックアップの失敗ではない（3.6 の対象外）。
- 反例:
  - `merge --left local --right develop` で develop のファイルだけを書き換えたのに、ローカルのファイルもバックアップされている。
  - 新しく作ったファイルについて、存在しないバックアップを指す `backup` が出力に入っている。
- 確認方法: ローカルの書き込み先の結合テストで、1 方向のマージの後に、`rollback --list --target <読み込むだけの側>` にそのバックアップセッションが出ないことを確かめる。
  新しいファイルだけを作るマージで、出力に `backup` が無く、`rollback --list` にセッションが出ないことを確かめる。
- TUI の `w` はこの要件の対象外とする（6 章の既知の制限）。

### 3.6 バックアップが取れなければ書き込まない

- 成功条件: `[backup] enabled = true` のとき、バックアップが取れなかったファイルは上書きも削除もしない。
  3.10 の記録（3.12・3.13 の判断に使う）に必要な情報（本当のパス、symlink だったかどうか）が得られない場合も、バックアップが取れなかったものとして扱う。
  - CLI: そのファイルを結果の失敗一覧（`failed`）に出し、その項目の `error` を `"backup failed: <原因>"` にする。同じ操作の他のファイルの処理は続ける。
    `--delete` の失敗も同じ文言にする（今の `"Backup failed, deletion aborted: …"` を置き換える）。
    rollback が戻す前に取るバックアップ（現在の内容の退避）が取れなかったファイルも、戻さずに同じく失敗として出す。
  - TUI: ステータス行に `Backup failed: <原因>` を出し、書き込まない。`w` では、どちらかの側のバックアップが取れなければ両側とも書き込まない。
- 集約先の場所が決まらない場合:
  - CLI: 書き込みを伴う操作全体をエラーで止める。`rollback` は `--list`・`--dry-run` を含め、`enabled` の値に関係なくエラーで終える（集約先を読めないと動けないため）。
  - TUI: 起動して差分の表示はできるが、書き込みの操作はすべて `Backup failed: <原因>` を出して断る。
- 反例: 集約先に書き込めない状態でマージしたら、警告だけ出て書き込み先が上書きされた。
- 確認方法: ローカルの書き込み先の結合テストで、集約先を書き込み不可にしてマージ・`--delete`・rollback を実行する。
  書き込み先が変わっていないこと、`failed` の項目の `error` が `backup failed:` で始まることを確かめる。
  TUI の振る舞いは、書き込みを判断する処理を状態と結果の組で表す純粋関数にし、単体テストで確かめる。

### 3.7 バックアップを無効にしたとき

- 成功条件: `[backup] enabled = false` のときは、範囲内のすべての経路（TUI の symlink マージを含む）でバックアップを取らずに書き込む。
  集約先の場所が決まらなくても、rollback 以外の書き込みは止めない（rollback は 3.6 のとおりエラーで終える）。rollback は戻す前のバックアップを取らずに戻す。
- 反例: `enabled = false` なのに TUI の symlink マージでバックアップが作られる。
- 確認方法: ローカルの書き込み先の結合テストで、`enabled = false` の設定でマージした後、集約先にバックアップセッションが作られないことを確かめる。

### 3.8 書き込み先ごとの区別

- 成功条件: バックアップは書き込み先ごとに区別して保存し、探し出す。
  - リモートの書き込み先は、ホスト名・ポート・root_dir の組で決まる。root_dir は設定に書いた文字列から末尾の `/` だけを除いたもの。
  - ローカルの書き込み先は、root_dir を設定の読み込み時のカレントディレクトリを基準に絶対パスにし、末尾の `/` を除いたもので決まる。symlink は辿らない。
  - ログインユーザー名は含めない。ホストの別名（`127.0.0.1` と `localhost` など）は別の書き込み先として扱い、名前解決はしない。
  - `rollback --target <名前>` は、今の設定でその名前が指す書き込み先のバックアップだけを扱う。表示にはサーバ名を使う。
- 反例:
  - 設定で `develop` の host を `old.example.com` から `new.example.com` に変えた後、`rollback --list --target develop` に古いホストのバックアップが出る。
  - 別プロジェクトの設定にある同名の `develop`（別ホスト）のバックアップが一覧に混ざる。
  - ローカルの root_dir `current` が `releases/A` から `releases/B` に付け替えられた後、過去のバックアップが一覧から消える。
- 確認方法: 書き込み先の識別を設定とカレントディレクトリから計算する処理を純粋関数にし、単体テストで確かめる。
  ローカルの書き込み先 2 つを使う結合テストで、一方の一覧に他方のバックアップが出ないことを確かめる。

### 3.9 バックアップセッションと ID

- 成功条件:
  - 1 回の書き込み操作につき、セッション ID を操作の開始時に 1 回だけ決める。
  - ID の形は、UTC の日時 `YYYYMMDD-HHMMSS`（15 文字）に、省略可能な `-N`（N は 2 以上の 10 進数）を付けたもの。
    `-N` は、同じ日時の ID がすでにあるときだけ付ける。
  - ID は集約先全体で重複しない。別々の操作が同じ秒に始まっても、同時に走っても、同じ ID にならない。
  - `sync` で複数の書き込み先に書く場合は、全書き込み先で同じ ID を使う。
  - ID の並び順は、日時部分の順、同じ日時なら N を数値として比べた順（`-N` の無いものが最初）。
    `rollback --list` の表示順、`rollback` で `--session` を省略したときに選ぶ「最新」は、この順に従う。
  - `rollback --session` は `-N` の付いた ID も受け付ける。期限切れの判定（3.16）には日時部分を使う。
  - 何も記録しなかったバックアップセッション（新しいファイルを作るだけの操作、確認で取り消した操作など）は、集約先に残さず、一覧にも出さない。
- 反例:
  - 1 秒以内に 2 回マージしたら、2 回分のファイルが 1 つのバックアップセッションに混ざっている。
  - `20260914-155250-10` が `20260914-155250-9` より古いものとして扱われる。
  - 新しいファイルを作るだけのマージの後、`--session` を省略した rollback が空のセッションを選んで何も戻さない。
- 確認方法: 時刻を注入できる形にし、同じ時刻で 2 回セッションを作る単体テストで、ID が異なることを確かめる。
  ID の解析と並び順は純粋関数の単体テストで確かめる。同時に作る場合の重複防止は、並行してセッションを作る結合テストで確かめる。

### 3.10 symlink の記録

- 成功条件: 書き込み先のパスの途中または末尾に symlink があるとき、バックアップには次の 2 種類のどちらかを記録する。
  - 辿って書いた記録: 書き込みが symlink を辿って、その先にある通常ファイルを上書き・削除した場合。
    中身（3.4）に加えて、実際に書き込んだ先の本当のパス（途中の symlink を全部辿りきったパス）を記録する。
  - symlink を置き換えた記録: マージが末尾の symlink そのものを通常ファイルや別の symlink に置き換えた、または削除した場合。
    symlink だったことと、リンクの中身（リンク先を表す文字列）を記録する。リンク先のファイルの中身は保存しない。
- パスに symlink が無い通常ファイルでも、本当のパスは記録する（3.12・3.13 の判断に使う）。
- 反例: 末尾が symlink の書き込み先を置き換えるマージの後、バックアップにはリンク先ファイルの中身が通常ファイルとして入っていて、symlink だった記録がない。
- 確認方法: ローカルの書き込み先の結合テストで、末尾が symlink のパス（置き換え）と、途中のディレクトリが symlink のパス（辿って書く）をそれぞれマージする。
  記録の形式（8 章）は直接読まず、`rollback --list` の表示（3.14）と、rollback の結果（3.12）で確かめる。

### 3.11 rollback の書き戻し方

- 成功条件: rollback は集約先に保存した中身だけを使って戻す。書き込みは通常のマージと同じ経路で行う。
  既存のファイルがあればその所有者と権限を維持する。無ければ、通常のマージで新しくファイルを作るときと同じ扱いにする。
- 反例: rollback で戻したファイルの所有者が、書き込み経路（エージェントか SSH か）によって変わる。
- 確認方法: ローカルの書き込み先の結合テストで、既存ファイルの権限が rollback の前後で変わらないことを確かめる。
  リモートはリモートの E2E テストで確かめる。

### 3.12 rollback は symlink を壊さない

ここで「symlink を壊す」とは、symlink を通常ファイルに置き換えること、symlink を削除すること、
バックアップ時とは別の先に向いた symlink を辿ってその先を書き換えることをいう。

- 成功条件: rollback は各ファイルについて、戻す直前にパスを辿り直し、次の順に判断する。最初に当てはまったものを適用する。この判断は `--force` でも変わらない。
  1. 記録が「symlink を置き換えた記録」（3.10）→ 戻さず、スキップ理由 `"symlink restore not supported"`。
  2. 本当のパスが記録と違う → 戻さず、スキップ理由 `"path now resolves to a different location"`。
  3. どれにも当てはまらない → 戻す（辿った先を書き換える）。
- 本当のパスは、存在する symlink を辿れるところまで辿って求める。末尾がリンク切れの symlink なら、そのリンクが指すパスが本当のパスになる（記録とは違うので 2 に当たる）。
- 権限が無い、symlink が循環している、リモートでコマンドが失敗した等でパスを辿り直せなかったファイルは、戻さずに結果の `failed` に出し、
  その項目の `error` を `"cannot resolve path: <原因>"` にする。
- 戻す先に今ファイルが無い場合は 3.13 に従う。
- スキップしたファイルは結果の `skipped` に出す。この判断で 1 件でもスキップした場合、または辿り直せずに失敗した場合、rollback の終了コードは 2 にする。
  機密ファイルのスキップが終了コードに与える影響は今までどおり（戻したファイルが 0 件なら 2）。
- `--dry-run` でも書き込み先に接続してパスを辿り、スキップ・失敗になるファイルと理由を表示する。`--dry-run` の終了コードは今までどおり 0。
- この規則は、ローカルを含むすべての書き込み先に適用する。
- 反例:
  - root_dir が `current -> releases/A` のときにマージし、その後 `current` が `releases/B` に付け替えられた。rollback すると `releases/B` のファイルが書き換わる。
  - マージ時は通常ファイルだったパスが今は symlink になっていて、rollback するとその symlink が通常ファイルに置き換わる。
  - symlink の安全のためにスキップしたファイルがあるのに、rollback が終了コード 0 で終わる。
- 正しく戻す例: リモートの `public/uploads` が `/mnt/shared/uploads` への symlink で、マージで `public/uploads/banner.txt`（実体は `/mnt/shared/uploads/banner.txt`）の中身が変わった。
  `public/uploads` のリンクがそのままなら、rollback で `/mnt/shared/uploads/banner.txt` の中身が元に戻る。
- 確認方法:
  - ローカルの書き込み先の結合テストで、上の各場合と判断の順番（1 と 2 が重なる場合を含む）、リンク切れの symlink、循環する symlink を実際に作って再現し、
    書き込み先の状態・スキップ理由・失敗理由・終了コードを確かめる。
  - リモートの E2E テストで、root_dir 自体が symlink の構成（`current -> releases/A`）を含めて、付け替え前後の rollback を確かめる。

### 3.13 戻す先にファイルが無い場合（削除したファイルの rollback）

- ここで「ファイルが無い」とは、リンクを辿らずに確かめて、そのパスに何も無いことをいう。末尾がリンク切れの symlink の場合は「無い」に当たらず、3.12 で判断する。
- 成功条件: 戻す先に今ファイルが無い場合、次の順に判断する。
  1. 記録が「symlink を置き換えた記録」→ 戻さず、スキップ理由 `"symlink restore not supported"`。
  2. 親ディレクトリが無い → 戻さず、スキップ理由 `"parent directory no longer exists"`。
  3. 親ディレクトリの本当のパスが、記録した本当のパスの親と違う → 戻さず、スキップ理由 `"path now resolves to a different location"`。
  4. どれにも当てはまらない → ファイルを作って戻す。
- スキップと失敗（親ディレクトリを辿り直せなかった場合の `"cannot resolve path: <原因>"` を含む）の結果の出し方と終了コードは、3.12 と同じ。
- rollback が戻す前に取るバックアップは、戻す先にファイルが無いので何も記録しない（3.5）。
- 反例:
  - `merge --delete` で消したファイルを rollback しても、「本当のパスが記録と違う」（今は何も無いため）としてスキップされ、戻らない。
  - 親ディレクトリごと消えていたので、rollback が新しくディレクトリを作ってファイルを置いた。
- 確認方法: ローカルの書き込み先の結合テストで、`--delete` の後の rollback でファイルが戻ること、
  親ディレクトリの symlink を付け替えた後と、親ディレクトリを消した後はそれぞれの理由でスキップされることを確かめる。

### 3.14 rollback の一覧表示

- 成功条件: `rollback --list` は、`--target` で指定した書き込み先（省略時はローカル）の、集約先にあるバックアップセッションを表示する。
  - 中身のある記録（通常ファイル、辿って書いた記録）は、今までどおりテキストでは `path (N bytes)`、JSON では `path` と `size` で出す。
  - symlink を置き換えた記録は、テキストでは `path -> link_target (symlink)`、JSON ではその項目に `"link_target"` を追加し、`size` は出さない。
  - 期限切れ（3.16）のセッションは、今までどおりテキストでは `[expired]`、JSON では `"expired": true` を付けて出す。
  - 記録が欠けた・壊れたセッションは出さない。それで一覧のコマンド全体がエラーになることはない。
- 反例: symlink を置き換えた記録が一覧に出ず、rollback を実行して初めて `"symlink restore not supported"` のスキップに気づく。
- 確認方法: ローカルの書き込み先の結合テストで、symlink を置き換えた記録を含むバックアップセッションの一覧を、テキストと JSON の両方で確かめる。
  記録の欠けたセッションは、集約先の中から、バックアップした中身と同じ内容のファイルを探して消すことで作る（4 章の「手で消す」操作の再現。中の構成には依存しない）。
  そのセッションが一覧に出ず、`--session` で指定した rollback が何も書き込まずにセッションが見つからない扱いで終わることを確かめる。

### 3.15 CLI 出力の互換

- 成功条件: merge・sync・rollback の JSON 出力とテキスト出力の形は、次の変更を除いて変えない。
  - 3.14 の変更（symlink を置き換えた記録に `"link_target"` を足し、`size` を出さない）
  - 3.5 の変更（新しく作ったファイルの結果に `backup` を出さない）
  - 3.13 の変更（戻す前のバックアップを記録しなかったファイルの rollback の結果に、JSON の `pre_rollback_backup` とテキストの `(pre-rollback backup: …)` を出さない）
  - 3.12・3.13 の新しいスキップ理由と、3.6・3.12 の新しい失敗理由
  `"backup": "{セッションID}/{相対パス}"` の値の書き方は変えない。集約先の絶対パスは出さない。
- 反例: merge の JSON の `backup` に `/home/user/.local/share/remote-merge/backups/...` という絶対パスが入る。
- 確認方法: ローカルの書き込み先の結合テストで merge・sync・rollback を実行し、JSON の `backup` が `{セッションID}/{相対パス}` の形で絶対パスを含まないこと、
  既存の項目名と値の型が変わっていないことを確かめる。

### 3.16 古いバックアップの掃除

- 成功条件:
  - 掃除は、TUI の起動時と、CLI の `merge`・`sync` の開始時（`--dry-run` のときは除く）に行う。`rollback` は、どのオプションでも掃除しない。
  - 掃除の対象は、今の設定に出てくる書き込み先のバックアップセッションのうち、期限切れのもの。今の設定に出てこない書き込み先のバックアップは削除しない。
  - 期限切れは「セッション ID の日時部分（UTC）からの経過時間が、今の設定の `retention_days` × 24 時間以上」と定める。一覧の期限切れ表示（3.14）も同じ判定を使う。
  - `enabled = false` のときも掃除は行う。集約先の場所が決まらないときは掃除をしない。
  - 期限切れのセッションを `rollback --force` で戻す機能は今までどおり残す（掃除されるまでは戻せる）。
- 反例:
  - 保持日数ちょうどのセッションが、一覧では期限切れと表示されるのに削除されない（または逆）。
  - プロジェクト A で CLI を実行したら、プロジェクト B だけが使う書き込み先のバックアップが消える。
  - `rollback --list` を実行しただけで期限切れのセッションが消え、`--force` で戻せなくなる。
- 確認方法: 時刻を注入できる形にし、境界の前後のセッションについて「期限切れ表示」と「削除対象」が一致することを単体テストで確かめる。
  書き込み先 2 つを使う結合テストで、設定に無い書き込み先のバックアップが残ること、`rollback --list` の後も期限切れのセッションが残ることを確かめる。

### 3.17 既存の `.remote-merge-backup/` の扱い

- 成功条件: ツールは既存の `.remote-merge-backup/`（リモートの root_dir 配下・ローカルのプロジェクトディレクトリ配下）を読みも書きもしない。
  rollback の一覧にも出さない。ファイル一覧・差分の対象からは、今までどおり除外する。
- 反例: 既存の `.remote-merge-backup/` の中身が「片側にしかないファイル」として差分に大量に出る。
- 確認方法: ローカルの書き込み先の結合テストで、書き込み先に既存の `.remote-merge-backup/` を置いた状態で、status に出ないこと、rollback の一覧に出ないことを確かめる。

### 3.18 エージェントからバックアップ機能を取り除く

- 成功条件: リモートで動くエージェントは、バックアップの作成・一覧・復元の機能を持たない。
  リモートの root_dir 配下にバックアップを作る処理が、コード上に存在しない。
- 反例: エージェントのプロトコルに、`backup_dir` を受け取ってファイルを作るリクエストが残っている。
- 確認方法: レビューで、エージェントのプロトコルと SSH で実行するコマンドの組み立て処理に、バックアップ用の経路が残っていないことを確かめる。
  挙動としては 3.1 の確認で担保する。

### 3.19 ドキュメント

- 成功条件: 次の記述が、集約先の場所・4 章の約束・この仕様の挙動と一致している。
  - `spec.md` のバックアップポリシー、rollback の節（バックアップ構造、終了コード、期限切れと `--force`、セッション ID の形式の制約）
  - `skills/remote-merge/SKILL.md` のバックアップ構造の記述
  - `skills/remote-merge/references/json-schemas.md` の `backup`、`rollback --list`、rollback の結果の説明
- 反例: `SKILL.md` に `.remote-merge-backup/{session_id}/{relative_path}` と書かれたままになっている。
- 確認方法: 人が読んで確認する。

### 3.20 書き込み先への読み書きを差し替えられること

- 成功条件: 範囲内の書き込みの経路は、書き込み先への読み書き（中身の読み込み、書き込み、削除、パスを辿る処理）を、差し替え可能な形で受け取る。
  テストでは、一時ディレクトリをリモートの書き込み先の代わりに使って、merge・sync・`--delete`・rollback を SSH なしで実行できる。
  差し替えは読み書きの部分を入れ替えることで行い、テストからしか呼ばれないメソッドを本番のコードに足さない。
- 反例: merge のバックアップの挙動を確かめるテストが、localhost への SSH 接続が無いと実行できず、`#[ignore]` 付きでしか書けない。
- 確認方法: 3.1〜3.17 の「ローカルの書き込み先の結合テスト」が、SSH なしで通常のテスト実行（コミット前のチェックを含む）で走ることを、人がテストの一覧と実行結果で確かめる。

## 4. 集約先について利用者に約束すること

- 集約先の場所は 3.2 のとおり。
- 集約先の中身を手で消しても、失われるのはバックアップだけで、ツールの動作は壊れない。一部だけ消されて記録が欠けたセッションは、一覧に出さず、戻しもしない。
- 書き込み先ごとの置き場所には、その書き込み先のホスト名・ポート・root_dir（ローカルなら root_dir の絶対パス）を書いた、人が読めるファイルを必ず置く。
  これを見れば、どの書き込み先のバックアップかを人が探し出せる。

中のそれ以外のフォルダ構成や記録の形式は、この約束を満たす範囲で実装が決める（8 章）。

確認方法: 人が読めるファイルがあること自体は、ローカルの書き込み先の結合テストで、集約先の中にその書き込み先の root_dir の絶対パスを含むファイルがあることで確かめる（ファイルの場所と名前には依存しない）。

## 5. 作らないもの

- 集約先の場所を設定ファイルで変更する機能
- 既存の `.remote-merge-backup/` の自動削除・自動移行
- マージで新しく作ったファイルを rollback で削除する機能（別の仕様で扱う）
- rollback で symlink を作り直して戻す機能（別の仕様で扱う）
- 設定から消えた書き込み先のバックアップを掃除する機能
- マージが末尾の symlink を通常ファイルに置き換える挙動の見直し、および root_dir の外への書き込みがエージェントから SSH への切り替えで通ってしまう件の修正
  （「マージ時の symlink の扱い」の仕様で扱う）

## 6. 既知の制限

- TUI の `w` は、変更した側に関係なく両側に書き込み、両側をバックアップする（保存先は集約先）。
  変更していない側も同じ中身で書き直され、更新日時が変わる。TUI は WebView 実装時に削除する予定のため直さない。
- マージで通常ファイルを symlink に置き換えた場合、rollback では元に戻せない（戻すと symlink を壊すため、3.12 で「本当のパスが違う」としてスキップされる）。
- rollback できるのは、マージを実行したマシンからだけ。別のマシンで行ったマージは一覧に出ない。
- 同じ書き込み先を、`retention_days` の違う 2 つのプロジェクトから使うと、片方の掃除がもう片方のバックアップセッションも自分の保持日数で消す。
- ファイル数が多い書き込みでは、上書き直前の内容を読み直す（3.4）ぶん、今より遅くなる。

## 7. 却下した案

- リモート側の保存先を設定で指定できるようにする: 設定ミスや既定値のままで、公開ディレクトリ配下に作るリスクが残る。
- diff 表示時に読み込んだ内容をバックアップに使う: 表示から書き込みまでの間の変更を取りこぼし、戻した中身が実際に上書きした内容と違いうる。
- 集約先全体を今の設定の保持日数で掃除する: プロジェクトごとに違う保持日数を設定している場合に、他のプロジェクトのバックアップを予想外に消す。
- rollback 先が今 symlink ならスキップする（種類だけで判断する）: リモートだけ symlink を経由するパスへの正しい更新まで戻せなくなる。
- TUI の `w` も変更した側だけ書き込むように直す: 削除予定の TUI に、undo の記録の改修まで入れることになる。
- rollback の開始時にも掃除する: 期限切れの表示と、期限切れのセッションを `--force` で戻す機能が使えなくなる。
- rollback で、本当のパスが同じでも末尾が symlink かどうかの種類が変わっていればスキップする: 本当のパスが同じなら書き戻しても symlink を壊さず、実際の運用で起きる状況として再現もできない。
- ローカルの書き込み先を symlink を辿ったパスで区別する: root_dir の symlink を付け替えた瞬間に過去のバックアップが一覧から消え、3.12 の安全チェックまで届かない。

- 集約先の中のフォルダ構成と記録の形式。4 章の約束を満たすどの構成でも、この仕様の挙動は変わらない。
