# マージ時の symlink の扱い（移行元）

> kotowari IR への移行前の要件。実装済みの現行仕様としては扱わない。

## 1. 目的

マージ・sync がリモートやローカルの symlink を壊さないようにする。あわせて、書き込み先の root_dir の扱いを 3 つの経路（エージェント・SSH・ローカル）で揃え、
symlink が絡むと表示や判定が狂う既存の不具合を直す。直す不具合は、root_dir 自体が symlink のときリモートのツリーが空に見えること、
同じサイズ・同じ更新日時で中身が違うファイルをファイル指定の `merge` が黙って無視すること、の 2 つ。

背景: 今のマージは、書き込み先の末尾が symlink だとリンクを消して通常ファイルを置く。読み込む側が symlink で書き込み先が通常ファイルなら、通常ファイルを消して symlink を作る。
どちらも「バックアップのローカル集約」の仕様（`docs/spec/local-backup-store.md`、以下「① の仕様」）で「symlink を壊す」と定めた操作そのもので、rollback でも戻せない。
また、エージェントは symlink を辿った先が root_dir の外なら書き込みを拒否するが、拒否されると SSH 経路に切り替わって結局書く。3 経路で判定が違うため、どの経路を通るかで結果が変わる。

用語（「末尾の symlink」「途中の symlink」「書き込み先」）の定義は `CONTEXT.md` に従う。root_dir 自体が symlink である場合は「途中の symlink」に含めず、3.6 で別に扱う。

## 2. 範囲

対象になる操作:

- CLI: `merge`（ファイル指定・ディレクトリ指定、`--ref` 付きの 3way を含む）、`merge --delete`、`sync`（`--delete` を含む）、`status`、`diff` のツリー取得
- TUI: サービス層を共有する部分だけ。TUI 固有の対応はしない（TUI は凍結中）。共有する判定がスキップや拒否を返したとき、TUI は既存のエラー表示（ステータス行）にその理由の文言を出して書き込まない。

書き込み先がリモートかローカルかを問わず、リモート → ローカル、ローカル → リモート、リモート → リモートの全方向を対象にする。
① の仕様の記録と rollback の判断はどの方向でも同じ規則で動いているため、この仕様の「壊さない」も書き込み先の側で決め、方向で変えない。

対象にしないもの: rollback の挙動（① の仕様のまま）、ハンクマージ（symlink を今までどおり拒否する。`spec.md` のハンクマージの節）。

## 3. 要件

各要件の「成功条件」は外から観察できる結果、「反例」はその要件が満たされていない状態の例、「確認方法」は証拠の取り方を示す。
確認方法に出てくる「ローカルの書き込み先の結合テスト」は、① の仕様 3.20 の仕組みで一時ディレクトリを書き込み先の代わりに使い、通常のテスト実行で走るテストを指す。
「実機 E2E」は 3.13 で定める、環境変数で指定した実際の SSH サーバに対して走る `#[ignore]` 付きのテストを指す。

この仕様で「symlink を壊す」とは、末尾の symlink を通常ファイルやディレクトリに置き換えること、または末尾の symlink を削除することをいう。
① の仕様 3.12 の 3 つ目（バックアップ時とは別の先に向いた symlink を辿って書く）はマージには当たらない。マージには「バックアップ時」に相当する基準が無く、途中の symlink を辿って書くのは正当な更新として扱う（3.4）。

「種類」とは、書き込み先や読み込む側のツリーに現れる、通常ファイル・symlink・ディレクトリの 3 つをいう。symlink はリンク先が何であれ（ディレクトリでも、リンク切れでも）symlink と数える。
種類の判定はマージ開始時に取得したツリーで行う。

### 3.1 マージは symlink を壊さない

- 成功条件:
  - 書き込み先の末尾が symlink で、読み込む側が通常ファイルまたはディレクトリのとき、マージはそのパスに何も書かず、削除もせず、スキップとして結果に出す（理由は 3.3）。symlink はマージ前と同じリンク先のまま残る。
  - `merge --delete`・`sync --delete` で削除の対象になったパスが書き込み先で symlink のとき、削除せずスキップとして結果に出す。
  - 読み込む側も書き込み先も symlink のときは、今までどおりリンク先の文字列を書き換える。書き込み先の symlink がディレクトリを指していても、その中に新しい symlink を作るのではなく、symlink 自体を付け替える（`ln -sfn` 相当）。
- 反例:
  - ローカルの `config.json` が通常ファイル、develop の `config.json` が `/etc/app/config.json` への symlink のとき、マージ後に develop の `config.json` が通常ファイルになっている。
  - `--delete` の後、develop にだけあった symlink が消えている。
  - リンク切れの symlink が `--delete` で消される。
- 確認方法: ローカルの書き込み先の結合テストで、末尾が symlink の書き込み先に通常ファイルをマージし、symlink がリンク先ごと残ること、結果の `skipped` にそのパスが入ることを確かめる。
  `--delete` で symlink（リンク切れを含む）が残ることを確かめる。symlink 同士のマージでリンク先が書き換わること、書き込み先がディレクトリを指す symlink でも symlink 自体が付け替わることを確かめる。
  実機 E2E（3.13）で SSH とエージェントの両経路について同じことを確かめる。

### 3.2 マージは種類の違うものを置き換えない

- 成功条件:
  - 読み込む側と書き込み先の種類が違うとき（通常ファイル・symlink・ディレクトリのどの組み合わせでも）、マージは書き込み先に何もせずスキップとして結果に出す。書き込み先の通常ファイルの中身は変わらず、ディレクトリの配下も変わらず、symlink のリンク先も変わらない。
  - 読み込む側がディレクトリで書き込み先が symlink のとき、そのパス自体はスキップとして結果に出し、配下のファイルは 3.7 のとおり扱う。読み込む側が symlink で書き込み先がディレクトリのときは、書き込み先のディレクトリの配下は「書き込み先にだけある」として今までどおり触らない。
  - 種類が同じもの同士（通常ファイル同士、symlink 同士、ディレクトリ同士）は今までどおりマージする。
  - `--ref`（3way）の ref 側の種類はこの判定に関与しない。3way マージがこの要件や 3.1 でスキップになるときも、結果の形（`ref_badge` を含む）は今までのスキップと同じ。
- 反例:
  - ローカルの `current` が `releases/A` への symlink、develop の `current` が通常のディレクトリのとき、マージ後に develop の `current` が symlink になっている。
  - ローカルの `config.json` が symlink、develop の `config.json` が通常ファイルのとき、マージ後に develop の `config.json` が symlink になっている（① の仕様 6 章で「rollback で戻せない」とした状況）。
- 確認方法: ローカルの書き込み先の結合テストで、symlink → 通常ファイル、symlink → ディレクトリ、ディレクトリ → symlink、通常ファイル → ディレクトリの各組み合わせをマージし、書き込み先の種類と中身が変わらないこと、`skipped` に入ることを確かめる。
  実機 E2E で symlink → 通常ファイルの組み合わせを両経路で確かめる。

### 3.3 スキップの理由と終了コード

- 成功条件:
  - 3.1・3.2 のスキップは、結果の `skipped` に `path` と `reason` を出す。`reason` は次のどれか。
    - 種類の違い: `"type mismatch: left is <kind>, right is <kind>"`。`<kind>` は `regular file`・`symlink`・`directory` のどれか。left は読み込む側、right は書き込み先。
    - `--delete` の対象が symlink: `"symlink deletion not supported"`
    - 種類を判定するためにパスを辿れなかった（権限が無い、symlink が循環している、リモートでコマンドが失敗した等）: `"cannot resolve path: <原因>"`。
      同じ文言を ① の仕様は rollback の `failed` の `error` に使う。この仕様の `merge`・`sync` では `skipped` の `reason` に使う（コマンドが違うので読み分ける）。
  - テキスト出力は、今まであるスキップと同じ 1 行の形式 `  - <path> (skipped: <reason>)` で出す。
  - 上の理由によるスキップが 1 件でもあれば、`merge` の終了コードは 2。`sync` では、その書き込み先の `status` を `"partial"` にし、全体の終了コードは 2。
  - 今まであるスキップ（書き込み先にだけあるファイル、機密ファイル）と 3.9 の `"identical"` は今までどおり終了コード 0 で、`sync` の `status` にも影響しない。
  - `--dry-run` でも同じスキップを同じ理由で出す。`--dry-run` の終了コードは 0。
- 反例:
  - 末尾の symlink をスキップしたのに終了コードが 0 で、LLM エージェントが全件成功と読む。
  - `--dry-run` では何も出ず、実行して初めてスキップに気づく。
  - 機密ファイルのスキップだけがある実行の終了コードが 2 になる。
- 確認方法: ローカルの書き込み先の結合テストで、各理由のスキップを 1 件ずつ含む merge の JSON の `reason` とテキストの行と終了コード、`--dry-run` の出力と終了コード、機密ファイルのスキップだけのときの終了コードを確かめる。
  sync は書き込み先 2 つのうち片方だけ末尾が symlink の構成で、片方だけ `"partial"` になり終了コードが 2 になることを確かめる。

### 3.4 途中の symlink は辿って書く

root_dir は「マージの対象になる範囲」を決める設定であって、書き込み先を閉じ込める安全境界ではない。共有ディレクトリを symlink で root_dir の下に見せる構成はレガシー環境で普通にあり、そこへの書き込みは正当な更新として扱う。

- 成功条件:
  - 書き込み先のパスの途中（親ディレクトリのどこか）に symlink があるとき、マージは symlink を辿ってその先に書く。辿った先が書き込み先の root_dir の外でも書く。
  - この判定は、エージェント・SSH・ローカルの 3 経路で同じ。エージェントが「辿った先が root_dir の外」を理由に拒否することはなく、そのために SSH 経路へ切り替わることもない。
  - 辿った先に既にファイルがあれば、① の仕様 3.5・3.10 のとおりバックアップを取ってから書く（書き込み先のツリーで「読み込む側にだけある」と表示されていても同じ）。
- 反例:
  - develop の `public/uploads` が `/mnt/shared/uploads` への symlink のとき、エージェント経路では `public/uploads/banner.txt` の書き込みが失敗し、SSH 経路では成功する。
  - `/mnt/shared/uploads/banner.txt` が既にあるのに、バックアップ無しで上書きされる。
- 確認方法: ローカルの書き込み先の結合テストで、root_dir の外を指す途中の symlink 越しにマージし、リンク先に書かれること、既存ファイルがあればバックアップが取られることを確かめる（既存のテスト `merge_through_an_intermediate_symlink_updates_the_resolved_file` を含む）。
  エージェントの書き込みの単体テストで、root_dir の外を指す symlink 越しの書き込みが拒否されないことを確かめる。
  実機 E2E で両経路について同じことを確かめる。

### 3.5 root_dir の範囲の検査は字面だけで行う

- 成功条件:
  - 3 経路とも、マージ対象の相対パスに `..` の成分が含まれるか、相対パスとして渡された値が絶対パスであるときだけ拒否する。symlink を解決した先が root_dir の外かどうかは検査しない。
  - 拒否されたファイルは結果の `failed` に出し、`error` は 3 経路で同じ 1 つの文言 `"path traversal detected: <相対パス>"` にする。操作全体は止めず、他のファイルの処理は続ける。
  - symlink を作るマージ（symlink 同士）で、リンク先の文字列に `..` や絶対パスが含まれていても拒否しない。ローカルの symlink をそのまま複製する。
  - エージェントが chown / chmod を行うときに、symlink を解決した実パスに対してだけ行う規定（`spec.md` のセキュリティ考慮事項）は変えない。
- 反例:
  - エージェント経路だけが `-> /etc/app/config.json` という symlink の作成を拒否し、SSH 経路では作れる。
  - `../outside/file` の拒否文言が経路によって違う。
- 確認方法: 字面の検査を、相対パスを受け取って拒否か通過かを返す純粋関数 1 つにし、単体テストで `..` の成分・絶対パス・通常のパスの各入力を確かめる。
  3 経路がその関数を使うことは、経路ごとの単体テストで同じ入力が同じ文言で拒否されることで確かめる。ローカルの書き込み先の結合テストで、`..` を含むパスの merge が `failed` の `error` にこの文言を出すことを確かめる。
  エージェントの単体テストで、`..` や絶対パスをリンク先に持つ symlink の作成が成功することを確かめる。

### 3.6 root_dir 自体が symlink でもツリーが見える

- 成功条件:
  - 書き込み先の root_dir がディレクトリへの symlink のとき、`status`・`diff`・`merge`・`sync` のツリー取得は、起点だけ symlink を辿って配下のファイルを列挙する。配下の symlink は辿らない（今までどおり）。設定の root_dir に末尾の `/` があってもなくても同じ結果になる。
  - SSH 経路では、再帰スキャンと 1 階層のスキャンのどちらの `find` コマンドにも、起点だけ辿るオプション `-H` を付ける（実機の CentOS 5、findutils 4.2.27 で使えることを確認済み）。
  - エージェント経路は include 指定の有無にかかわらず同じ。include 指定ありのとき配下が捨てられる不具合はコードからの推論で未再現のため、先に再現するテストを書き、再現したときだけ直す。再現しなければ、この項目は何もしない。
  - ローカルの書き込み先は今までどおり（既に起点を実パスに解決して走査している）。
- 反例:
  - `root_dir = "/srv/current"`（`releases/A` への symlink）で `status` を実行すると、リモートのファイルが全部「ローカルにだけある」と出る。
  - `root_dir = "/srv/current/"` なら見えるのに `"/srv/current"` では見えない。
- 確認方法: SSH の `find` コマンドを組み立てる純粋関数が返した文字列を、ローカルのシェルで、root が symlink の一時ディレクトリに対して実行し、配下が列挙されることを結合テストで確かめる（再帰スキャンと 1 階層スキャンの両方）。
  エージェントのツリー走査の単体テストで、root が symlink のとき include 指定あり・なしの両方で配下が列挙されることを確かめる。
  実機 E2E で、root_dir が symlink の構成で `status` にリモートのファイルが出ることを両経路で確かめる。

### 3.7 途中のディレクトリ symlink の配下は辿らない

- 成功条件: 書き込み先の途中にディレクトリへの symlink があるとき、ツリー取得はその配下を列挙しない。結果として、読み込む側の配下のファイルは「読み込む側にだけある」と表示される。
  そのファイルをマージすると 3.4 のとおり symlink を辿って書き、辿った先に既にファイルがあればバックアップを取る。
- 反例: develop の `public/uploads` が symlink のとき、`status` がリンク先のファイルを列挙し、リンク先の巨大なディレクトリ全体を走査する。
- 確認方法: ローカルの書き込み先の結合テストで、途中のディレクトリ symlink の配下のファイルのマージがリンク先に書かれることを確かめる。
  ツリー取得については、3.6 と同じ方法（SSH の `find` コマンドをローカルで実行、エージェントの走査の単体テスト）で、途中のディレクトリ symlink の配下が列挙されないことを確かめる。
  実機 E2E で、途中のディレクトリ symlink の配下が `status` に出ないことを両経路で確かめる。
- これは既知の挙動として `spec.md` に明記する（3.14）。

### 3.8 status の内容比較から symlink を除外する

`status` は、サイズと更新日時で Modified と判定したペアのうちサイズが同じものだけ中身を読み比べて、同じなら Equal に直す（以下「既定の絞り込み」）。`--checksum` はすべてのペアで中身を読み比べる。

- 成功条件: 既定の絞り込みでも `--checksum` でも、片方でも symlink のペアは中身を読み比べない。両方 symlink ならリンク先の文字列が同じときだけ Equal、違えば Modified。片方だけ symlink なら Modified。
- 反例: ローカルの `config.json` が通常ファイル、develop の `config.json` がそのファイルと同じ中身を指す symlink で、サイズが偶然一致すると `status` が Equal と出す。
- 確認方法: 中身を読み比べる対象を絞る純粋関数の単体テストで、片方が symlink のペアが対象から外れることを確かめる。ローカルの書き込み先の結合テストで、上の反例の構成が Modified と出ることを確かめる。

### 3.9 ファイル指定の merge は中身で判定する

- 成功条件:
  - パスにファイルを指定した `merge` は、サイズと更新日時が同じでも中身を読み比べ、違えば書く。比べ方は `status --checksum` と同じ。symlink 同士はリンク先の文字列で比べる。
  - 中身まで同じなら書かず、結果の `skipped` に `{"path": …, "reason": "identical"}` を出す。テキストは 3.3 の 1 行の形式。終了コードは 0。
  - `merge <ファイル> --checksum` は受け付け、結果は `--checksum` なしと同じ（常に中身で判定するため）。`sync` でファイルを指定したときも同じ。
- 反例:
  - 同じサイズ・同じ更新日時で 1 文字だけ違うファイルを `merge <path> --force` しても、何も書かれず終了コード 0 で `merged` も `skipped` も空。
  - 中身が同じファイルを指定したとき、JSON が空配列だけで、何もしなかった理由が読み取れない。
- 確認方法: ローカルの書き込み先の結合テストで、同じサイズ・同じ更新日時（秒精度で揃える）・違う中身のファイルを指定してマージし、書き込み先が変わることを確かめる。同じ中身のときに `skipped` の `reason` が `"identical"` で終了コード 0 になること、`--checksum` を付けても同じ結果になることを確かめる。
  実機 E2E で同じサイズ・同じ更新日時・違う中身の構成を両経路で確かめる。

### 3.10 ディレクトリ指定の merge と sync に `--checksum` を付ける

- 成功条件:
  - `merge <ディレクトリ>` と `sync <ディレクトリ>` に `--checksum` を追加する。指定時は `status --checksum` と同じ比べ方で差分を決める。指定しないときは今までどおりサイズと更新日時で判定する（`status` の既定と同じ）。
  - `--checksum` なしでは、同じサイズ・同じ更新日時で中身が違うファイルは Equal として今までどおり黙ってスキップされる（既知の制限、6 章）。
- 反例: `merge src/ --checksum` を付けても、同じサイズ・同じ更新日時で中身が違うファイルが書かれない。
- 確認方法: ローカルの書き込み先の結合テストで、同じサイズ・同じ更新日時・違う中身のファイルを含むディレクトリを `--checksum` あり・なしでマージし、ありのときだけ書かれることを確かめる。sync も同じ。

### 3.11 読み取りに失敗したファイルは失敗として出す

- 成功条件:
  - `merge`・`sync` の中身の読み比べ（3.9・3.10）でどちらか片側でも読み取りに失敗したファイルは、同じか違うかの判定から外し、結果の `failed` に `path` と `error` を出す。`error` は `"read failed: <原因>"`。終了コードは、今までの `failed` があるときと同じ（`merge` は 2、`sync` はその書き込み先が `"failed"` または `"partial"` になり全体は 2）。
  - `status` の既定の絞り込みと `--checksum` でどちらか片側でも読み取りに失敗したファイルは Equal にせず、Modified のままにする。
- 反例:
  - 両側とも読めないファイル（権限が無い等）が Equal と判定され、マージ対象から外れて何も出ない。
  - 片側だけ読めないファイルが Modified と判定され、空の内容で書き込み先が上書きされる。
- 確認方法: ローカルの書き込み先の結合テストで、読み込む側だけ読み取り不可、両側とも読み取り不可の各構成で merge を実行し、書き込み先が変わらず `failed` の `error` が `read failed:` で始まること、同じ構成で `status` が Modified のままであることを確かめる。

### 3.12 CLI 出力の互換

- 成功条件: `merge`・`sync`・`status` の JSON 出力とテキスト出力の形は、次の変更を除いて変えない。
  - 3.3 の新しいスキップ理由と、`sync` の `status` が `"partial"` になる新しい条件
  - 3.2 により、ディレクトリのパスが `skipped` に現れること（今まではファイルのパスだけ）
  - 3.9 の `"identical"`、3.11 の新しい失敗理由
  - 3.10 の `--checksum` フラグ
  - 3.5 の拒否文言の統一（`failed` の `error`）
- 反例: `skipped` の項目名や `failed` の項目名が変わり、`skills/remote-merge/references/json-schemas.md` の形と合わなくなる。
- 確認方法: ローカルの書き込み先の結合テストで merge・sync の JSON の項目名と値の型が今までと同じことを確かめる。

### 3.13 実機 E2E を自動で走らせる

- 成功条件:
  - `tests/e2e_testenv.rs` の E2E テストを、Docker のコンテナではなく、環境変数で指定した実際の SSH サーバに対して走るように置き換える。`docker exec` でリモート側を操作する経路は削除する。① の仕様で既にある rollback のケースは、置き換えた仕組みの上で残す。
  - 接続先は次の環境変数で受け取る。値はリポジトリの外にだけ置く。
    - `REMOTE_MERGE_E2E_SERVER_TOML`: サーバ設定の TOML のパス（今までどおり `[servers.develop]` を含む）
    - `REMOTE_MERGE_E2E_REMOTE_BASE`: リモートの作業ディレクトリの絶対パス（テストはこの配下にだけ書く。今までの `REMOTE_MERGE_E2E_CONTAINER` はなくす）
    - `REMOTE_MERGE_AGENT_BINARY`: エージェントのバイナリのパス（今までどおり）
  - リモート側の準備と検査は、TOML のユーザー名・ホスト・ポート・鍵だけを使ってシステムの `ssh` で流す。鍵交換やホスト鍵のアルゴリズムの指定はテストが組み立てず、利用者の `~/.ssh/config` に任せる。
  - どれかの環境変数が無ければ、無い変数名を示すメッセージで失敗する。黙って成功にしない。
  - テストが自分で組み立てるメッセージ（失敗の説明、残したパスの案内）にはホスト名・ユーザー名・鍵のパスを含めず、場所は環境変数名で示す。
  - 各ケースは `<作業ディレクトリ>/<ケース名>-<経路>`（`<経路>` は `ssh` か `agent`）を自分で作り、その中に書き込み先の root_dir と、root_dir の外を指す symlink の先になるディレクトリの両方を置く。準備のときにケースのディレクトリ直下へ目印のファイル `.remote-merge-e2e-case` を置く。
  - 成功したケースは終了時に自分のケースのディレクトリだけを消す。次のどれかに当たるときは消さずに失敗する: 目印のファイルが無い、作業ディレクトリの値が空、作業ディレクトリの値が `/` か `~` かホームディレクトリそのもの、作業ディレクトリの値が絶対パスでない。失敗したケースは消さず、残した場所をケース名で出力する。作業ディレクトリ自体は消さない。
  - 最低限、次のケースを SSH 経路とエージェント経路の両方で持つ。
    1. root_dir が symlink のとき、`status` にリモートのファイルが出る（3.6）
    2. 途中の symlink 越しのマージがリンク先に書く（3.4）
    3. 末尾がリモートの symlink でローカルが通常ファイルのマージがスキップされる（3.1）
    4. ローカルが symlink でリモートが通常ファイルのマージがスキップされる（3.2）
    5. `--delete` の対象が symlink ならスキップされる（3.1）
    6. 同じサイズ・同じ更新日時で中身が違うファイルをファイル指定の merge が書く（3.9）
    7. 途中のディレクトリ symlink の配下が `status` に出ない（3.7）
  - テストは `#[ignore]` のままにし、CI では走らせない。この仕様の実装サイクルの完了条件と、リリース前の確認に「実機 E2E が全ケース通ること」を入れる。
- 反例:
  - 環境変数が無いときにテストが成功扱いで終わる。
  - テストの失敗出力にホスト名が出て、それが issue やコミットに貼られる。
  - テストが作業ディレクトリごと消す。
- 確認方法: 環境変数が無い状態で E2E を実行し、無い変数名を含むメッセージで失敗することを確かめる。
  後片付けの判定（目印の有無、作業ディレクトリの値が上の拒否条件に当たるか）は単体テストで確かめる（判定をどう切り出すかは実装に委ねる）。
  実機 E2E の各ケースが通ることは、実装サイクルの完了時とリリース前に環境変数を揃えて実行した結果（全ケースの成否のログ）を証拠にする。成功したケースのディレクトリが消え作業ディレクトリが残ることは、テスト自身が終了時に確かめる。

## 5. 作らないもの

- root_dir の外への書き込みを拒否する機能（途中の symlink を辿った先が root_dir の外でも書く。3.4）
- 途中のディレクトリ symlink の配下をツリーで列挙する機能（3.7）
- 末尾の symlink を辿ってリンク先のファイルを上書きする機能
- ツリーの取得から書き込みまでの間に書き込み先の種類が変わったことを検出する機能（6 章）
- TUI 固有の対応（サービス層の変更が波及する範囲だけ）
- エージェントがエラーを返したときに無効化されて以降の操作が SSH 経路になる仕組みの見直し（別件）
- SSH 経路で `rm -f` の失敗が成功扱いになる件の修正（別件）
- CI から社内のサーバへ到達して E2E を回す仕組み
- Docker の CentOS 5 コンテナに対する E2E（`testenv/` 自体はレガシー環境と負荷のテスト用として残す）

## 6. 既知の制限

- 種類の判定はマージ開始時のツリーで行う。ツリーの取得から書き込みまでの間に書き込み先の末尾が symlink に変わっても検出せず、通常ファイルへの書き込みとして symlink を辿ってリンク先に書く（① の仕様 3.10 の「辿って書いた記録」が残る）。
- 途中のディレクトリ symlink の配下は「読み込む側にだけある」と表示される（3.7）。
- `--checksum` を付けないディレクトリ指定の merge・sync では、同じサイズ・同じ更新日時で中身が違うファイルは Equal として黙ってスキップされる（`status` の既定と同じ）。
- 末尾の symlink を意図的に通常ファイルへ置き換えたいときは、書き込み先で手で symlink を外してからマージする。
- 実機 E2E は社内のサーバに届く端末からしか走らせられない。CI では走らない。

## 7. 却下した案

- root_dir の外への書き込みを 3 経路とも拒否する: 共有ディレクトリを symlink で root_dir 配下に見せる構成がレガシー環境で普通にあり、① の仕様 3.12 の「正しく戻す例」とも矛盾する。
- 末尾の symlink を辿ってリンク先のファイルを上書きする: 複数のデプロイ先で共有している設定ファイルを書き換えてしまい、置き換えるより影響が大きい。
- 末尾の symlink を今までどおり通常ファイルで置き換える: ① の仕様で「symlink を壊す」と定めた操作そのもの。
- ファイル指定の merge を比較せず必ず書く: 実行のたびにバックアップセッションができる。
- 途中のディレクトリ symlink の配下をツリーで列挙する: 走査の範囲が root_dir を越えて予測できなくなり、循環の対策も要る。
- root_dir の起点をリモートで実パスに解決してから `find -P` に渡す: `find -H` が実機（CentOS 5、findutils 4.2.27）で使えると確認でき、出力パスの前置きを変えずに済む。
- 実機 E2E を人がスモークテストとして実行する: 利用者が人手の実行を望まない。
- CI から VPN 等で社内のサーバへ到達して E2E を回す: 社内のサーバを CI に繋ぐのは許容されない。

## 8. 実装に委ねること

- 実機 E2E のハーネスの内部構造（後片付けの判定の切り出し方を含む）。環境変数名・ケース・目印のファイル名・後片付けの規則は 3.13 で固定しており、どの構造でも挙動は変わらない。
