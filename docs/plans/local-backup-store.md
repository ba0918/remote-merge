# 実装計画: バックアップのローカル集約

## 目標

マージ・sync・rollback のバックアップを、ローカルの集約先 1 か所だけに保存するようにする。
バックアップが取れなければ書き込まず、rollback が symlink を壊さない状態を、ブランチ `feat/local-backup-store` の上で完成させる。

## 仕様

`docs/spec/local-backup-store.md`（以下「仕様」）。この計画は仕様の本文を写さない。各ステップで挙げる節を必ず読むこと。
用語「バックアップセッション」「書き込み先」は `CONTEXT.md` の定義に従う。

## 進め方と理由

### 最初に、SSH なしでテストできる形にする

仕様の確認方法の大半は「ローカルの書き込み先の結合テスト」（仕様 3 章の冒頭と 3.20）で、今のコードではこれが 1 本も書けない。理由は 2 つある。

- 書き込み先ごとの振り分けが、すべて `CoreRuntime` の中にある。`src/runtime/side_io.rs` が `Side` ごとに `match` しているので、リモートのサーバを差し替える入口がない。
- CLI の `run_*` 関数（`src/cli/merge.rs`・`sync.rs`・`rollback.rs`）は、中で `CoreRuntime::new` を作り、結果を `println!` で出して終了コードだけを返す。
  そのため、テストから呼んでも JSON の中身を検査できない。

だから最初の 2 ステップで、次の形を作る。

- `CoreRuntime` という型はそのまま残し、その中で書き込み先への読み書きを trait の向こうに切り出す。
  呼び出し側（サービス層、CLI、`src/cli/tolerant_io.rs`、`src/service/source_pair.rs`、TUI の handler）の型は変えない。`TuiRuntime.core` も具体型のまま。
- 書き込み先の実装は、`CoreRuntime` を作るときに渡す。渡す場所は、本番の組み立ての場所（CLI の各入口と、TUI の `src/runtime/bootstrap.rs`）に揃える。
  テストも同じ入口に実装を渡す。だから、テストからしか呼ばれないメソッドは生まれない（仕様 3.20、CLAUDE.md の「4. Testability」）。
- テストで差し替えに使うのは、本番のローカルファイルシステムの実装（本当のパスの解決を含む）を、一時ディレクトリを root にして作ったものだけ。
  これを、設定上はリモートのサーバ名（例: `develop`）に割り当てる。`tests/` に独自の偽物の実装を置いてはいけない。
  偽物を使うと、symlink の判断のテストが製品ではなく偽物を確かめることになるため。
- CLI の各 `run_*` は、「出力の構造体と終了コードを返す関数」と「それを表示するだけの薄い関数」に分ける。テストは前者を呼ぶ。
  確認プロンプト（`src/cli/rollback.rs` の `confirm_prompt`、`src/cli/sync.rs` の `stdin` 読み込み）がある経路は、テストでは `force` 相当で呼ぶ。
  仕様 3.12 により、symlink の判断は `--force` でも変わらないので、これで判断を確かめられる。

### 集約先の場所もテストから切り離す

集約先の場所は、組み立ての場所で環境変数とホームディレクトリから決める（仕様 3.2）。
決まった結果は「場所」か「決まらない」のどちらかを表す値として `CoreRuntime` に渡す。
ライブラリ経由のテストは、この値として一時ディレクトリを渡す。`CoreRuntime::new_for_test` 系も一時ディレクトリを使う。
バイナリを起動する既存のテスト補助（`tests/common/mod.rs` の `CliEnv::cmd` と `remote_merge_cmd`）は `env_clear()` の後に `HOME` だけを戻している。
そのままだと開発者の本物の `~/.local/share/remote-merge/backups/` に書くので、テストごとの一時ディレクトリを `XDG_DATA_HOME` として渡すように変える。
テストのプロセスの中で `std::env::set_var` を使って切り替えるのは禁止する（テストが並列に走ると互いに干渉するため）。

### その後の順番

純粋関数で書ける部品を先に作る。対象は、集約先の場所、書き込み先の識別、セッション ID、期限切れの判定、rollback の判断の順番。
次に I/O 側を、保存 → 本当のパスと symlink の記録 → 一覧 → 復元 → symlink の判断 → 掃除、の順に積む。
一覧は保存が書いたものを読み、復元は一覧と同じ読み出しを使うので、この順になる。
仕様の確認方法の多く（3.5、3.8 など）は `rollback --list` を通して確かめるので、それらの確認は一覧のステップにまとめる。

TUI は凍結対象なので、CLI 側で作ったものを呼ぶように、最小限だけつなぎ替える（仕様 6 章の既知の制限）。
古いバックアップ処理（今の `CoreRuntime::create_backups`、リモート用の SSH コマンド、エージェントの 3 リクエスト）は、呼び出し元が全部なくなるまで今の意味のまま残す。消すのは後半の専用のステップ。
リモートでの実機確認と、ドキュメントを最後に置く。

### 層の置き場所

CLAUDE.md の決まりに従う。

- 純粋な判断は、副作用のないモジュールに置く。対象は、ID の解析と並び、期限切れ、書き込み先の識別、rollback の判断の順番。
  今の `src/service/rollback.rs` は純粋関数だけでできているので、判断はここに寄せてよい。
- I/O は `src/runtime/` 側に置く。
- `src/backup/mod.rs` は今、純粋関数と I/O が混ざっているので、触るときに分けてよい。

`CoreRuntime` の接続状態のフィールド（`agent_clients`、`ssh_clients`）は、今の場所から移さない。
`src/runtime/bootstrap.rs` と `src/handler/reconnect.rs` が直接読んでいるため。リモート用の実装は、これらを `CoreRuntime` から借りて使う形にする。

## 実装者に任せること（計画全体）

- trait・モジュール・型・関数の名前と、内部の分け方。上の「層の置き場所」は守ること。
- 集約先の中のフォルダ構成と記録の形式（仕様 8 章）。仕様 4 章の約束を満たすこと。
- セッション ID の重複を防ぐ仕組み（例: ディレクトリの排他的な作成）。同時に走る 2 つの操作でも重ならないこと。
- リモートで本当のパスを求める仕組み。エージェントに新しいリクエストを足すか、SSH で実行するコマンドを使うかは任せる。条件は次の 2 つ。
  - testenv の CentOS 5（bash 3.2、coreutils 5.97）で動くこと。
  - root の外を指す場合でも本当のパスを求められること。今のエージェントの `validate_path` は root の外に出る本当のパスを拒否するが、仕様 3.12 の「正しく戻す例」は root の外を指す。

## 計画として決めたこと

仕様が決めていない実装上の扱いのうち、承認された挙動を変えないものを、ここで固定する。

- 書き込み直前の読み直し（仕様 3.4）は、ファイルごとに、そのファイルの上書き・削除の直前に行う。全ファイルを先にまとめて読むことはしない。
  まとめて読むと、読んでから書くまでの間の変更を取りこぼすため。遅くなることは仕様 6 章で受け入れ済み。
- CLI の merge・sync・rollback の計算関数と、集約先への保存の API は、現在時刻を引数（または時刻の供給元）で受け取る。本番は組み立ての場所で `Utc::now` を渡す。
  同じ秒のセッションや期限切れのセッションを、集約先の中の構成に触れずにテストで作るため。
- 書き込み先のパスを、リンクを辿らずに確かめられない場合（symlink の循環などで `lstat` 相当が失敗する場合）は、「新しいファイル」ではなく「本当のパスが得られない」として扱う。
  つまり仕様 3.6 のとおり `backup failed: ` にする。
  今のツリー取得は、存在を確かめられないパスを空として扱う（`src/runtime/side_io.rs` のサブパスのツリー取得）。そのままだと新規ファイルと誤判定されるため、ここで決めておく。
- エージェントの版は、この計画では上げない（版の変更はリリースの手続きで行う）。
  エージェントのプロトコルを変えるステップ（6 と 12）の後、実機で確かめるとき（ステップ 13）は、testenv 上に置かれた既存のエージェントを消してから実行する。
  今の仕組みでは `--version` の文字列が同じなら置き直されないため。
- 既存の localhost 向けの `#[ignore]` テスト（`tests/cli_merge.rs`、`tests/cli_rollback.rs`）は、リモートとローカルが同じファイルシステムを共有する前提で書かれている。
  そのため testenv には向けられない。これらはステップ 12 で仕様 3.1 に合わせて書き換える。
  実行できるのは localhost への SSH が使える環境だけ。使えなければ「未実行」と報告する。
  仕様が求めるリモートでの確認は、ステップ 13 で新しく作る testenv 向けの E2E で行う。

## 止まる条件（計画全体）

次のどれかに当たったら、手を止めて理由を添えて差し戻す。

- 仕様の意味が足りない、または承認された内容から外れないと進めない。
- 取り消せない操作、特権が要る操作、危険な対象への操作が必要になった。
- 変更が「変更してよい範囲」の外に広がり始めた。
- やり方を変えても 2 回続けて進まない。
- 差し替えの注入口を作るために、`src/app/` や `src/ui/` の設計変更が必要になった。
- 既存のテストが、仕様で認めた変更以外の理由で出力の変更を求めた。
  仕様で認めた変更とは、3.15 の一覧、3.17 による `.remote-merge-backup/` の無視、3.6 の失敗文言の統一のこと。

## テストの実行

コミット前に、次の順で実行して全部通すこと。

```
cargo fmt --all --check
cargo clippy --all-targets --all-features -- -D warnings
cargo nextest run --all-features
```

これは `scripts/pre-commit` と同じ中身。今のクローンでは、このフックが `.git/hooks` に入っていないことがある（`scripts/setup-hooks.sh` が未実行）。
だから、フックに頼らず手で実行する。`cargo nextest` が無い環境では `cargo test --all-features` を使う。

`#[ignore]` 付きのテストは、ステップ 12・13 でだけ実行する（`cargo test --test <name> -- --ignored`）。

## 範囲外

仕様 5 章「作らないもの」のとおり。特に次の 2 つは、この計画では直さない。どちらも、仕様「マージ時の symlink の扱い」（未作成）で扱う。

- マージが末尾の symlink を通常ファイルに置き換える挙動（`MergeAction::ReplaceSymlinkWithFile`）

## ステップ 1 — 書き込み先への読み書きを `CoreRuntime` の中で切り出す

目的: 書き込み先ごとの振り分けを trait の向こうに移し、あとで差し替えられる形にする。挙動は一切変えない。
仕様: 3.20「書き込み先への読み書きを差し替えられること」。

前提: なし。

変更してよいもの: `src/runtime/`（`core.rs`、`side_io.rs`、`remote_io.rs`、`mod.rs`、新しいモジュール）。

完了の条件: 次の 3 つがすべて成り立つこと。
- `src/runtime/side_io.rs` で `Side` によって分岐している操作が、すべて trait の向こうの実装（ローカル用とリモート用）に移っている。
  操作には次が含まれる。
  - 読み込み（単体・まとめて・バイト列）、書き込み、削除、権限変更、symlink の作成
  - 更新日時の取得、ツリーの取得（サブパスを含む）
  - 接続・切断、書き込み先が使えるかの確認（今の `is_side_available`）
  - 今のバックアップの作成・一覧・復元
- `CoreRuntime` の公開メソッドの形（引数と戻り値）は変わっていない。接続状態のフィールドの場所も変わっていない。
- 既存のテストがすべて通り、clippy の警告も無い。

示し方: test — 新しく作ったローカル用の実装について、振る舞いごとに 1 本書く（CLAUDE.md の「テストの無い変更は禁止」に従う）。
- root の下のファイルを読み書き・削除できる。
- symlink を作れる。
- サブパスのツリーを取れる。
- 使えるかの確認で「使える」を返す。
この 4 本に加えて、「テストの実行」の 3 コマンドがすべて通ること。

実装者に任せること: trait の分け方（1 つにするか、読み込み・書き込み・ツリーで分けるか）、エージェントと SSH の切り替えをリモート用の実装の内側にどう置くか。

差し戻す条件: エージェントと SSH の切り替え（`with_agent`、`check_sudo_fallback`、`invalidate_agent`）の挙動を変えないと切り出せない場合。

## ステップ 2 — 注入口を作り、SSH なしの最初の結合テストを通す

目的: 本番とテストが同じ入口で書き込み先の実装を渡せるようにし、CLI の結果を検査できる形にする。
仕様: 3.20「書き込み先への読み書きを差し替えられること」。

前提: ステップ 1。

変更してよいもの:
- `src/runtime/core.rs`・`bootstrap.rs`・`mod.rs`
- `src/cli/merge.rs`・`sync.rs`・`rollback.rs`・`status.rs`・`diff.rs`
- `src/main.rs`
- `tests/common/`、新しい結合テストのファイル

完了の条件: 次の 3 つがすべて成り立つこと。
- 注入口の配線
  - `CoreRuntime` を作るときに書き込み先の実装を渡せる。
  - CLI の各入口と `bootstrap_tui` は、同じ注入口に本番の実装を渡している。
  - `CoreRuntime` を作る箇所（`run_merge`、`run_hunk_merge`、sync、rollback、status、diff、`TuiRuntime::new`）はすべて同じ入口を通る。
- 出力の分離: CLI の merge・sync・rollback・status は、出力の構造体と終了コードを返す関数と、それを表示する関数に分かれている。
  status はステップ 7 で 3.17 の確認に使う。diff は注入口の配線だけでよい。
- SSH なしの結合テスト: 一時ディレクトリを root にしたローカル用の実装を `develop` に割り当て、ローカル → develop の merge を呼ぶと、SSH に接続せずに一時ディレクトリのファイルが更新される。
  返ってきた出力の構造体に、そのファイルが merged として入っている。

示し方: test — RED → GREEN → REFACTOR。
結合テストを 1 本書く。内容は「差し替えた develop へのローカルからの merge が、SSH なしで書き込み先のファイルを更新し、結果に merged として出る」。
先にこのテストを書いて、今の構造では書けないこと・通らないことを確かめてから（RED）、注入口と出力の分離を行う（GREEN）。
このテストはバックアップを無効（`[backup] enabled = false`）にした設定で書く。集約先への保存はまだ無いため。

実装者に任せること: 注入の引数の形（構造体でまとめるか、サーバ名から実装を引く関数を渡すか）、出力の構造体を既存の `MergeOutput` などの型そのままにするか。

差し戻す条件: 出力を分けるために、JSON やテキストの出力の中身を変える必要が出た場合。

## ステップ 3 — 集約先の場所と書き込み先の識別

目的: バックアップを置く場所と、書き込み先ごとの区別を、純粋関数として決める。
仕様: 3.2「集約先の場所」、3.8「書き込み先ごとの区別」。

前提: なし（ステップ 1・2 と独立）。

変更してよいもの: `src/backup/`（または新しい純粋モジュール）。

完了の条件: 仕様 3.2 と 3.8 の成功条件を、それぞれ純粋関数として満たすこと。
- 集約先を決める関数は、`XDG_DATA_HOME` の値とホームディレクトリを引数に取り、「場所」か「決まらない」を返す。
- 書き込み先を識別する関数は、設定の値と、起動時のカレントディレクトリを引数に取る。カレントディレクトリの取得と受け渡しはステップ 5 で行う。

示し方: test — 振る舞いごとに 1 本。

## ステップ 13 — リモートでの確認

目的: 本物のリモート（testenv の CentOS 5）で、集約先への保存と、symlink を壊さない判断が動くことを確かめる。
仕様: 3.1、3.11、3.12（リモートの E2E）、3.20（SSH なしのテストが通常のテスト実行で走ること）。

前提: ステップ 1〜12。testenv のイメージを作れること（`testenv/rpms/` が揃っていること）。
エージェントの経路を確かめるには、musl 向けのビルド（`x86_64-unknown-linux-musl`）ができること。

変更してよいもの: `tests/`（新しい E2E のファイル。例: `tests/e2e_testenv.rs`）。

完了の条件:
- testenv に対して、次の E2E（`#[ignore]`）が、エージェント経由と SSH 経由の両方で通ること。
  リモートの Linux は musl 向けのエージェントを求める。普通の開発ビルドでは配れないので、何もしないと黙って SSH 経由だけになる。
  だから、どちらの経路で動いたかを E2E の中で確かめる（例: 置かれたエージェントのプロセスやファイルの有無を `docker exec` で見る）。
  - merge の後、リモートの root_dir に何も増えていない。
  - root_dir 自体が symlink（`current -> releases/A`）の構成で、付け替え前は rollback で戻る。
  - `releases/B` に付け替えた後は `path now resolves to a different location` でスキップされ、`releases/B` のファイルは変わらない。
  - 途中のディレクトリが root の外（testuser が書ける `/home/testuser/shared` など）を指す symlink のとき、rollback で辿った先の中身が戻る。
  - rollback の後、既存ファイルの所有者と権限が変わっていない。
- 3.20 の確認: ステップ 2〜11 で足した結合テストが、SSH なしの通常のテスト実行（`cargo nextest run --all-features`）で実行されている。
  テストの一覧と実行結果で確かめる。

示し方: external — 人またはエージェントが次の手順で実行し、E2E がすべて通ることと、上の 3.20 の確認を見る。

1. 鍵がなければ作る。
   `ssh-keygen -t rsa -b 2048 -f testenv/.ssh/id_rsa -N '' -C testenv`（`testenv/.ssh/` は git の管理外）
2. イメージを作る。`docker compose -f testenv/docker-compose.yml build`
3. E2E 用のコンテナを起動する。
   `docker run -d --name rm-testenv-e2e -p 127.0.0.1:2223:22 <作られたイメージ名>`
   イメージ名は `docker images` で確かめる。compose のプロジェクト名が `testenv` なら `testenv-centos5`。
   `testenv/setup.sh` と `docker compose up` は使わない。ホストの 2222 番を固定で使ううえ、10 万ファイルを生成するため。
   2223 番が使われていれば、空いている別の番号にする。既存のコンテナやサービスは止めない。
4. リモートの準備は E2E の中で `docker exec -u testuser rm-testenv-e2e ...` を使って行う。対象は `/srv/testdata` 配下の構成と、root の外のディレクトリ。
5. 置かれたエージェントが残っていれば消す（「計画として決めたこと」）。場所は設定の deploy_dir の既定（`/var/tmp`）の下。
6. エージェント経由で確かめるために、musl 向けにビルドする。
   `cargo build --target x86_64-unknown-linux-musl`（`.cargo/config.toml` はリンカに `x86_64-linux-musl-gcc` を指定している）
   できたバイナリのパスを `REMOTE_MERGE_AGENT_BINARY` に設定する。
   musl のターゲット（`rustup target add`）や `musl-tools` が無い場合、パッケージの導入は特権が要る操作なので、人に頼む。
   導入できなければ、SSH 経由だけを実行し、エージェント経由は「未確認」と報告する。
7. 環境変数を設定して、`cargo test --test e2e_testenv -- --ignored` を実行する。
   E2E は次の環境変数を読む。
   - `REMOTE_MERGE_E2E_SERVER_TOML`: `[servers.develop]` の表を丸ごと書いた TOML ファイルのパス。
     - host・port は、手順 3 の `docker run` の割り当て（例: `127.0.0.1`・`2223`）に合わせる。
     - user・auth・key・`[servers.develop.ssh_options]` の `kex_algorithms` は `testenv/config.toml` と同じ。
     - root_dir は既定値として書き、E2E が場面ごとに上書きしてよい（root_dir 自体が symlink の場面など）。
   - `REMOTE_MERGE_E2E_CONTAINER`: 準備と観察に使うコンテナ名。
   どちらかが無いときは、E2E は何もせずに失敗として終わる。黙って成功させないこと。
   E2E が書く設定には `[ssh] strict_host_key_checking = "no"` を入れ、HOME をテストごとの一時ディレクトリにする。
   作り直したコンテナはホスト鍵が変わるので、開発者の本物の `~/.ssh/known_hosts` を読み書きさせないため。
   エージェント経由と SSH 経由の切り替えは、設定の `[agent] enabled` で行う。
8. 終わったら `docker rm -f rm-testenv-e2e` で片付ける。

注意:
- testenv の起動には、WSL2 の `.wslconfig` の `vsyscall=emulate` が要る（CLAUDE.md）。
- この TOML ファイルは、リポジトリの外の一時ディレクトリに置く。コミットしない。

実装者に任せること: E2E の中の準備と観察の書き方。

差し戻す条件:
- testenv を起動できない場合。起動できないまま「確認済み」としてはいけない。未確認として報告する。
- CentOS 5 で本当のパスを求める仕組みが、エージェント経由か SSH 経由のどちらかで動かない場合。
